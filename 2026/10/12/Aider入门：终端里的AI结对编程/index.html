Aider 入门：终端里的 AI 结对编程

2026 年的 Coding Agent 已经很多了：有的嵌在 IDE 里，有的管一整支 Agent 团队。若你想要的是「打开终端，对着本地 Git 仓库结对改代码」，Aider 仍然是这条路上最直白的一种。

官网第一句就是定位：

AI pair programming in your terminal.

它跑在你的仓库里，你用自然语言说要改什么，它改文件、打出 diff，并自动做一次 Git 提交。不满意就 /undo。模型可以换，仓库还是你的。

本文按官方文档 aider.chat/docs 梳理：它是什么、五个核心机制、怎么上手，以及什么时候该用。

Aider 由 Aider AI LLC 维护，源码在 GitHub，协议为 Apache 2.0。项目有个常被引用的事实：每个版本里新增代码，大约七成是 Aider 自己写的——用 git blame 只统计源码行，不算文档和 prompt。

一、Aider 是什么？

按 Usage 的用法，一次会话大致是这样：

  1. 在 Git 仓库里启动 aider，把准备改的文件加进聊天
  2. 在 > 提示符下用自然语言描述改动
  3. 模型按指定的编辑格式吐出补丁，Aider 应用到文件
  4. 改动自动提交，带一段说明性的 commit message
  5. 看 diff，不行就撤销，再下一句

真正写代码的仍是你接上的 LLM。Aider 自己做的是结对编程这一层：选上下文、约束模型怎么改文件、把结果落进 Git。

能力 作用
聊天会话 只把要改的文件放进上下文，其余靠仓库地图补充
仓库地图 用类、函数签名和调用关系，让模型看见仓库骨架
聊天模式 code 改代码，ask 只讨论，architect 先方案后落盘
编辑格式 用搜索替换或整文件重写，而不是让模型自由发挥 diff
Git 自动提交、脏文件先落盘、/undo 撤销
Lint / Test 改完跑检查，失败就把报错喂回去修

一句话：它是终端里的结对程序员，把「对话」收成「可撤销的 Git 提交」。

二、它适合放在哪一层

和同主题的其他工具放在一起看，边界会清楚一些：

  • 想管一支有汇报线、预算和审批的 Agent 团队，看 Paperclip
  • 想要一台本机通用 Agent（桌面、CLI、MCP、可复用流程），看 Goose
  • 想在一个 Git 仓库里结对改代码，并且每一步都能 git log / git diff / /undo，用 Aider

Aider 一次只对着一个仓库。跨仓库时，官方建议在当前仓库里用 /read 把另一个仓库的关键文件或文档以只读方式拉进来，或者先导出对方的 repo map 再读入。

三、五个核心机制

把 Aider 用顺，通常摸清这五件事就够。

3.1 加文件，而不是把仓库倒进聊天

Usage 把「加入聊天」定义得很窄：这些文件模型既能看见全文，也能直接改。

会话中途用 /add 追加，用 /drop 移出，用 /read-only（或启动参数 --read）放只读参考。

官方反复强调的用法是：只加这次要改的文件。 多加无关文件，模型更容易跑偏，token 也更贵。FAQ 对「能不能把所有文件都加进去」的回答很直接：通常弊大于利。仓库其余部分，交给下一节的地图。

不指定文件也能启动。此时 Aider 会根据你的请求去猜该改哪些文件，并在需要时提议把它们加进会话。你自己先想清楚要动哪几个文件，结果通常更稳。

3.2 Repo map：给模型一张仓库骨架

Repository map 是 Aider 能在较大项目里干活的原因。每次请求，它会附上一张压缩过的仓库地图：有哪些文件、里面定义了哪些类和函数、关键签名长什么样。模型据此知道「别处已经有这个抽象」，也能判断自己还缺哪个文件的全文，再请你把它加进聊天。

地图太大时，Aider 不会整张塞进去。它把源文件当成图的节点，用依赖关系连边，再用图排序挑出和当前对话最相关的那一部分，塞进 token 预算。

  • --map-tokens 默认约 1024
  • 聊天里还没有文件时，地图会明显放大，方便模型先看清仓库
  • 较弱的模型默认可能关掉地图（启动时会看到 Repo-map: disabled），因为它们容易把地图里的代码当成要改的文件。需要时用 --map-tokens 1024 强制打开
  • 会话里可用 /map 看当前地图，/map-refresh 强制刷新

大仓库还可以收窄范围：在子目录里加 --subtree-only，或写一份语法和 .gitignore 相同的 .aiderignore，把无关目录排除在外。

3.3 四种聊天模式

默认是 code。提示符会标明当前模式：>、ask>、architect>。Chat modes 里四种模式分工如下：

模式 行为
code 按你的要求改文件。默认模式
ask 讨论方案、解释代码，不落盘
architect 主模型先出方案，编辑模型再把它翻译成具体补丁
help 问 Aider 自己：用法、配置、排错。也就是 /help

单条消息可以临时切模式，下一条回到当前模式：

想粘住某种模式，用 /chat-mode ask，或启动时加 --chat-mode ask。--architect 是架构模式的快捷开关。

文档推荐的日常节奏是 **先 /ask 后 /code**：在 ask 里把方案谈拢，切回 code 后甚至只说「按这个做」或 /ok 就够。前面的对话还在上下文里，模型知道要执行哪一版。

架构模式则是两次请求：

  1. 主模型（--model / /model）当架构师，用自然语言说明该怎么改
  2. 编辑模型（--editor-model，有内置默认）把方案写成 Aider 能应用的编辑块

推理强、落盘弱的模型适合放在架构师位置，再配一个擅长按格式改文件的编辑模型。同一模型担任两个角色也可以：多一轮往往比「又想方案又写补丁」更稳，代价是多一次调用、更慢、更贵。

3.4 编辑格式：规定模型怎么改文件

模型不是返回一段「我觉得代码应该长这样」的散文。Aider 用 edit formats 约束输出，再由程序应用到磁盘。常见几种：

格式 做法 典型场景
diff 搜索块 / 替换块，类似冲突标记 多数主力模型的默认高效格式
diff-fenced 同上，但文件路径写在围栏里面 Gemini 家族，避免围栏对不齐
udiff 简化过的 unified diff 早期用来抑制「用注释省略大段原文」
whole 返回整个文件的新版本 最简单，也最费 token
editor-diff / editor-whole 上面两种的精简提示词 只给架构模式里的编辑模型用

搜索块必须能在文件里唯一对上，Aider 才应用替换。格式和模型绑定：Aider 会按模型选默认格式，也可以用 --edit-format 强制指定。架构模式里编辑模型的格式用 --editor-edit-format，文档建议 editor-diff 或 editor-whole。

3.5 Git：每次改动都是一次提交

Git integration 是安全网，不是附加功能。

  • 目录还不是仓库时，Aider 会提议先 git init
  • 每次它改完文件，就用 Conventional Commits 风格写一条说明并提交
  • 提交说明交给 --weak-model（通常比主模型便宜），依据 diff 和聊天记录生成
  • 文件上已有未提交改动时，它会先把你的改动单独提交，再提交自己的，避免混在一次提交里，也避免它改坏时把你的工作卷进去
  • 作者或提交者名字会带上归属。当前配置里默认还会用 Co-authored-by trailer；作者名上的 (aider) 后缀可以用 --attribute-author 等开关控制

会话里和 Git 相关的命令：

命令 作用
/diff 看自你上一条消息以来的改动
/undo 撤销并丢弃 Aider 刚做的那次提交
/commit 把会话外改脏的文件提交掉
/git 跑一条原始 git 命令（输出不进聊天）

可以关掉自动提交（--no-auto-commits）、关掉「先提交脏文件」（--no-dirty-commits），或用 --no-git 完全不用 Git。最后一种官方不推荐：没有提交，就没有便宜的撤销，你得自己备份。

另外，Aider 默认提交时带 --no-verify，会跳过 pre-commit hook。要让 hook 真的跑，加上 --git-commit-verify。

五、谁适合用？谁可以先别用？

适合：

  • 主力环境是终端，希望 AI 改动以 Git 提交的形式留下
  • 仓库已经不小，不想把所有文件塞进上下文，愿意让 repo map 提供骨架
  • 想自己选模型（云端 API 或本地），并接受「加哪些文件」由人来判断
  • 需要 ask → code 的节奏：先把方案谈清楚，再允许它动文件

可以先别用：

  • 只想问一句答一句，不改仓库——普通聊天产品更合适
  • 需要同时编排多个角色、预算和审批——那是编排层的工作，Aider 是单个结对会话
  • 希望零配置吞下巨型 monorepo 还很快——它能工作，但大仓库要靠 .aiderignore 和 --subtree-only 收窄，官方也写明它没有为超大仓库的响应速度做过专门优化
  • 一次要改多个相互独立的 Git 仓库——当前一次会话只绑定一个仓库

六、小结

Aider 的主张可以压成一句：

在终端里结对编程：你点名要改的文件，它用仓库地图看懂其余部分，用固定编辑格式落盘，并用 Git 提交把每一次改动变成可以撤销的历史。

日常循环就是：/add 少量文件，/ask 对齐做法，/code 或 /architect 让它改，/diff 看结果，不对就 /undo。
