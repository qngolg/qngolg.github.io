Oh My Pi（omp）Advisor 入门：给主 Agent 配一位旁观评审

写代码的 Agent 越来越敢下刀：改文件、跑命令、开子代理——很快就能把仓库搅动起来。真正贵的往往不是「写得慢」，而是写偏了很久才发现。

omp 的 Advisor 想解决的正是这件事：再挂一个（或一组）独立评审模型，旁观主 Agent 的每一步，把遗漏需求、危险 API、验证薄弱、过度复杂之类的问题，在还能纠偏时塞回主会话。

官网 README 的说法很直白：

Pair a reviewer model to the advisor role and it reads every turn the main agent takes, injecting notes inline — a quiet aside, a concern, or a hard blocker.

主 Agent 是执行者；Advisor 是旁观者。两者各有上下文、各用各的模型，所以能抓住「干活的人赶着往前冲」时漏掉的东西。

本文按官方文档 omp.sh/docs/advisor 梳理：它是什么、怎么开、怎么定制、以及什么时候值得开。若你还不熟 omp 本体，可先看 中文文档 或 快捷键指南。

一、Advisor 是什么？

按 Advisor models 的定位：

Add an optional reviewer model that watches omp’s work, catches risky mistakes, and steers the main agent before they become expensive.

几个关键边界：

  1. 可选：默认可以不开；需要时再启用。
  2. 旁观，不是审批闸门：Advisor 不直接批准动作，也不直接改写主会话状态；它把意见注入主会话，由主 Agent（和你）决定怎么处理。
  3. 独立运行时：Advisor 有自己的 Agent、独立的 ToolSession（id 后缀 -advisor），不共享主 Agent 的文件快照、冲突状态与摘要缓存。
  4. 默认只读探查：默认工具是 read / grep / glob，外加专用的 advise；只有在 WATCHDOG.yml 里显式授权时，才可能拿到 edit / bash 等可变工具。

适合打开的场景，文档写得很明确：

  • 长变更、高风险变更
  • 不熟悉的仓库
  • 安全敏感工作
  • 独立评审的价值 > 极致速度 的时候

日常小改、追求吞吐时，保持关闭或用 /advisor off 即可。

三、会话里怎么用：/advisor 一族

命令 作用
/advisor 切换本会话 Advisor 总开关（不改磁盘上的 advisor.enabled）
/advisor on 为本会话启用 / 重建已配置的 Advisor
/advisor off 为本会话停掉 Advisor
/advisor status 看每个 Advisor 的状态、模型、上下文占用、token 与费用
/advisor dump 复制精简评审转录到剪贴板
/advisor dump raw 复制完整诊断转储（含指令、思考、工具活动；按敏感数据处理）
/advisor configure 打开交互式编辑器，改项目级或用户级 WATCHDOG.yml（仅 TUI）

on / off 都是会话级覆盖，不会偷偷改你的 config.yml。日常小任务临时关掉、重要重构再打开，很顺手。

状态行与卡片上会看到 Advisor 的旁注；主 Agent 读到后可以改道，也可以向你解释为什么不改。

四、三条意见等级：nit / concern / blocker

Advisor 通过 advise 工具把意见送回主会话，严重程度决定打断方式：

等级 投递方式 适合说什么
省略 / nit 不打断，在下一步边界批量并入主转录 清理、简化、低风险边角
concern 在允许时打断并纠偏；若主 Agent 已给出终局答案，多半变成可见卡片，等你下次继续 实质性风险、方向可能错、漏约束、幻觉 API
blocker 更强的打断；即使终局答案已出，通常仍会触发一轮，要求正视「交出了坏结果 / 未验证结果」 继续干下去明显浪费或必坏

还有几条「防吵」机制值得知道：

  • advisor.immuneTurns（默认 3）：成功投递一次 concern / blocker 后，接下来若干主回合里，新的 concern/blocker 会降级成不打断旁注，避免评审风暴。
  • 进行中的回合：评审还在追赶进行中的工作时，通常只允许 blocker 打断；nit / concern 会先记着。
  • 去重与空话过滤：同一条意见、或「lgtm / nothing to add」这类无内容短句会被压掉。
  • Plan 模式：本来会打断纠偏的意见，会改成可见卡片，避免抢掉「只由用户驱动收敛」的节奏。

你手动打断主 Agent（Esc 等）时，Advisor 也不会偷偷把已停止的回合再拉起来；意见会先记成卡片，等你发新消息或用继续快捷键时再进上下文。

五、WATCHDOG.md：只给评审员看的项目备忘

WATCHDOG.md 是 Advisor 专用 指引：追加到评审模型的系统提示里，不会像 AGENTS.md / RULES.md 那样塞进主 Agent 的日常上下文。

适合写：

  • 这个仓库最容易踩的坑
  • 危险 API / 鉴权边界
  • 架构红线与质量门槛
  • 「执行时太吵、但评审时很有用」的检查清单

示例：

发现路径（用户级 + 从 cwd 向上到仓库根）：

  1. ~/.omp/agent/WATCHDOG.md（可用 PI_CODING_AGENT_DIR 改目录）
  2. 项目里的 WATCHDOG.md 与 .omp/WATCHDOG.md

和普通上下文文件不同：不会在最近一层就停，多层项目备忘可以一起加载；更靠近 cwd 的内容更靠后、更突出。也支持与上下文文件相同的 @ 导入语法。

六、WATCHDOG.yml：多评审员编制

一个默认 Advisor 不够时，用 WATCHDOG.yml / WATCHDOG.yaml 声明编制。一旦发现任何编制条目，就替换「单一默认 Advisor」模式。

可用 /advisor configure 在 TUI 里原地编辑，也可手写：

字段速查：

字段 作用
顶层 instructions 所有 Advisor 共享的基线（多文件会拼接）
name 显示名；会规范化成 slug，用于会话 id 与转录文件名
enabled 单个开关，默认 true；false 仍可见，但是暂停
model 可选；省略则用 modelRoles.advisor
tools 可选；省略 = read/grep/glob；[] = 没有探查工具（仍有 advise）
instructions 该评审员的专项提示，支持 @ 导入

心智模型（官方 issue 里也强调过）：编制是多个彼此独立的被动评审员，不是互相商量的多 Agent 角色扮演。每人看同一段主会话增量，各自 advise，互不协调。

给可变工具时务必谨慎：它们跑在隔离的 Advisor ToolSession 里，但仍遵守会话的审批模式与按工具策略——只在信任该模型与工作区时再开。

搜索路径与 WATCHDOG.md 相同；同名 slug 由更具体的文件覆盖（项目叶子 > 祖先 > 用户级）。解析失败的文件会被跳过并打日志，避免一个坏项目配置弄死整场会话。

七、节奏与成本：syncBacklog / immuneTurns

可选旋钮仍在 config.yml：

设置 默认 用途
advisor.syncBacklog off off 从不为主 Agent 等评审追赶；"1" / "3" / "5" 在评审落后达到阈值时，最多暂停主 Agent 30 秒。"1" 最接近同步评审。YAML 里请给数字加引号（枚举字符串）
advisor.immuneTurns 3 打断成功后，多少个主回合内不再用 concern/blocker 硬打断。0 = 最严监督；调大 = 少打扰
tier.advisor none Advisor 请求的服务档；inherit 跟随主模型当前家族档位

费用上：Advisor 是另一路模型用量。/advisor status 与会话产物目录里的 __advisor*.jsonl 会单独记账；omp stats 也会把它们归到对应会话下。

实务建议：

  • 想紧盯：便宜一点的强模型 + syncBacklog: "1" + 较低 immuneTurns
  • 想省钱 / 少吵：更小模型、缩小编制、syncBacklog: off、提高 immuneTurns、收窄 WATCHDOG.md，或日常 /advisor off

多个 Advisor 会线性放大费用；重要审查可以开编制，例行任务别堆太多。

八、和子代理的关系

子代理默认不被评审。要给某个 agent 定义开评审，用 frontmatter 的 advisor: true（或显式模型字符串），或在 /agents hub 里按 agent 配置 task.agentAdvisor。

被开启的子代理会话会自己建一套 Advisor 子系统，并在该会话的 cwd 上重新发现 WATCHDOG.md / WATCHDOG.yml——与主会话隔离，也不是可互发消息的「同伴」。Agent Hub 里能看到只读的 advisor 转录，但不能把它当 peer 私信或 revive/kill。

九、排错速查

文档里常见几条：

  • 「enabled 了，但 no model」：补上 modelRoles.advisor，或给每个启用的编制条目写有效 model；用 /model、/login 确认提供商已装且已鉴权，再 /advisor off → /advisor on
  • 编制没生效：确认文件名是 WATCHDOG.yml / .yaml，放在用户目录、项目根或 .omp/，且 YAML / schema 合法
  • 太贵或太吵：换便宜模型、减编制、保持 syncBacklog: off、加大 immuneTurns、收窄 watchdog 说明，或临时 /advisor off
  • 想看评审到底看了什么：/advisor dump；需要完整诊断再用 dump raw（注意敏感信息）

十、什么时候该用？

可以把它想成「结对编程里的观察者」：

场景 建议
小改、熟悉仓库、赶速度 关着，或会话里 /advisor off
大重构、跨模块、安全相关 开默认 Advisor，写好 WATCHDOG.md
架构 + 安全要分头盯 WATCHDOG.yml 开两个专项评审员
CI / 脚本一次性审查 omp -p --advisor "..."

一句话：主 Agent 负责往前做；Advisor 负责在变贵之前喊停或纠偏。

更细的实现与边界（投递约束、隔离、转录路径等）见仓库文档 advisor-watchdog.md；日常用法以 omp.sh/docs/advisor 为准。原文持续更新，若有出入请以官网与 GitHub 为准。
