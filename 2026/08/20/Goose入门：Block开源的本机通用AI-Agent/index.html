Goose 入门：Block 开源的本机通用 AI Agent

2026 年的 Coding Agent 已经很多了。若你只是想「聊天改代码」，Claude Code、Cursor、OpenCode 都能上手。

Goose 想解决的问题略有不同：它不只是一个 coding CLI，而是一台跑在你电脑上的 通用 Agent 运行时——写代码是默认场景，研究、自动化、数据分析、可复用工作流同样在能力圈内。模型你自己选，扩展走 MCP，流程可以固化成 Recipes，还带桌面端和可嵌入的 API。

本文按「它是什么 → 核心概念 → 怎么装 → 什么时候该用」来介绍。和同场选手的横向对比，可对照前文 2026 流行 Coding Agent 能力对比。

一、Goose 是什么？

Goose 最初由 Block（Square / Cash App）开源，现由 Linux Foundation 旗下的 Agentic AI Foundation（AAIF） 治理，协议为 Apache 2.0。官方仓库常写的一句话是：

your native open source AI agent — desktop app, CLI, and API — for code, workflows, and everything in between

可以拆成四层意思：

关键词 实际含义
native / on-machine Agent 循环跑在本机，能直接碰你的文件、终端、开发环境
open source Apache 2.0；可审计、可 fork、可做定制 distro
desktop + CLI + API 同一套引擎，三个入口
general-purpose 不锁定「只写代码」；MCP 扩展到什么，能力就到什么

和「模型厂商自家 Agent」最大的差别是：Goose 不卖模型，也不锁模型。你可以用 Anthropic / OpenAI / Google 的 API，也可以走 OpenRouter、Azure、Bedrock，或者本机 Ollama；还可以通过 ACP 接已有的 Claude / ChatGPT / Gemini 订阅。软件本身免费，费用只来自你选的模型提供商。

二、形态：一套引擎，三个入口

  • Desktop：macOS / Linux / Windows 原生桌面应用，适合不想天天泡终端、又希望可视化管扩展和会话的人。
  • CLI：终端工作流、脚本化、CI/本地自动化；和多数 coding agent 的使用习惯最接近。
  • API / ACP：把 Goose 嵌进自家 UI，或作为外部 Agent 接到 Zed 一类支持 ACP 的编辑器里。

核心用 Rust 实现，强调性能和可移植。Block 后来基于 Goose 还做了桌面工作区 Berd——Berd 管项目/会话体验，Goose 继续当底下的 agent loop。对多数个人用户，直接用 Goose 桌面或 CLI 就够。

三、五个核心概念

把 Goose 用顺，通常只要摸清这五个词。

3.1 Providers：谁来思考

Provider 是 LLM 后端。Goose 官方宣称支持 15+ 提供商，常见包括：

  • 云端：Anthropic、OpenAI、Google、OpenRouter、Azure、Bedrock 等
  • 本地：Ollama 等
  • 订阅路径：经 ACP 复用已有 Claude / ChatGPT / Gemini 订阅

选型时记住一点：同一份模型，不同 harness 分数会差一截。公开评测里，Goose 在「同一 Claude 模型下的编码基准」往往打不过 Claude Code——它赢在中立、可扩展、可平台化，而不是「同模型极限发挥」。

3.2 Extensions：能力从哪来

扩展 = MCP server。Goose 把 MCP 当成扩展系统本身，而不是外挂插件协议。

内置扩展大致包括：

扩展 作用
Developer Shell、读改文件、代码分析（日常编码主力）
Computer Controller 系统自动化、网页抓取等
Memory 跨会话持久记忆
Todo 会话内任务清单
Extension Manager 运行时启停扩展
Chat Recall 检索、引用历史对话

社区与官方扩展目录很宽（文档常写 **70+**），GitHub、Slack、数据库、各类 SaaS 都可以接进来。传输上常见本地 stdio 与远程 SSE。配置一般落在 ~/.config/goose/；也可用 goose configure 交互式增减。

扩展目录：goose-docs.ai/extensions

3.3 Recipes：把「怎么做」固化成配方

Recipes 是 Goose 最有辨识度的能力之一：用 YAML 把任务说明、所需扩展、参数绑成 可分享、可重复执行 的工作流模板。

思路是：别每次口头重讲「先跑测试、再开 PR、再通知 Slack」，而是写成一份 recipe，团队复用，或用 CLI 非交互跑：

适合：发版检查清单、例行代码审查、数据拉取+报告、内部运维剧本。若你的目标是「把 Agent 用法定成组织资产」，Recipes 比纯聊天会话更对口。

3.4 Sessions：对话状态

Session 是一次完整的交互上下文。桌面端和 CLI 都会围绕 session 管理历史；配合 Memory / Chat Recall，可以跨会话找回「上次怎么定的」。

权限模式通常可在偏自治、逐步审批、手动确认、仅聊天之间切换，并叠加 per-tool 规则——本机 Agent 权限面很大，这层开关值得认真配。

3.5 Goosehints：项目级说明书

项目根目录放 .goosehints（以及常见的 AGENT.md / AGENTS.md 一类约定）可以告诉 Goose：技术栈偏好、目录约定、禁止操作、测试怎么跑。这和 Cursor Rules、Claude 的项目说明是同一类东西——把隐性团队知识写成 Agent 可读的约束。

四、安装与第一次跑通

4.1 安装 CLI

macOS / Linux / Windows：

macOS 也可用 Homebrew 装桌面端：

桌面安装包与更多平台说明见：Installation

4.2 配置模型

首次使用按文档走 Providers 配置：填 API Key，或接本地 Ollama，或走 ACP 订阅路径。没有可用 Provider，Goose 只是空壳。

4.3 典型第一次对话

装好后，在项目目录里用 CLI（具体子命令以当前文档为准）让它：

  1. 读 README，说明项目结构
  2. 跑现有测试
  3. 修一个明确的小 bug，并说明改了哪些文件

同时打开 Developer 扩展，确认它能读文件、跑 shell。这一步跑通，说明「本机循环 + 工具面」已经活了；再往下才是加 MCP、写 Recipe。

五、适合做什么、不适合做什么

5.1 很适合

  • 要模型自由 / 成本可控：BYOK、本地模型、多云切换
  • 要隐私与本机执行：代码默认只去你选的提供商；可配纯本地路径
  • 要把流程固化成资产：Recipes + 扩展目录，方便团队共享
  • 要平台能力：REST/ACP 嵌入、定制 distro（预装提供商、扩展、品牌）
  • 要基金会治理与宽松许可：AAIF + Apache 2.0，二次分发摩擦小

5.2 未必是第一选择

你更想要… 更该看
同一 Claude 模型下的编码质量上限 Claude Code
AI 原生 IDE 日常写代码体验 Cursor
终端手感、会话树、LSP/DAP Oh My Pi（omp）
规格驱动（先写 requirements/design/tasks） Kiro
长时间挂机、DeepSeek 成本曲线 Reasonix

一句话：Goose 强在「中立的本机 Agent 平台」；弱在「某一家模型的官方 harness 极限发挥」。

六、和周边生态怎么摆

2026 年更常见的用法不是「只装一个 Agent」，而是 一个宿主 + 多个循环：

  • 用 Zed（或其它 ACP 宿主）当编辑器，Claude Code 做质量敏感的重活，Goose 做便宜/本地/可扩展/可配方化的活
  • 用 Berd（若你跟 Block 桌面工作区路线）管体验，Goose 继续当 runtime
  • 用 MCP 把 GitHub、数据库、内部 API 接到扩展目录，而不是给每个 Agent 重写一遍集成

若你正在做「挂自家品牌的本机 Agent」或「可审计的企业内部 Agent 发行版」，Goose 的 Custom Distributions 叙事通常比纯 coding TUI 更贴。

七、小结

Goose 可以记成三句话：

  1. 本机通用 Agent：不只写代码，扩展到哪里，能力就到哪里。
  2. 协议与治理优先：MCP 当扩展系统，ACP 可嵌编辑器/UI，AAIF + Apache 2.0。
  3. Recipes 把用法变成资产：重复工作流值得写成配方，而不是每次重新聊天。

上手路径建议：装 CLI 或桌面 → 配一个 Provider → 用 Developer 扩展改一个小仓库 → 再加一两个 MCP → 最后把高频流程收成 Recipe。
