AI 时代的 TDD：让 Agent 按红绿重构写代码

AI 写代码很快。快到一种错觉：TDD 是上个时代给人用的，Agent 直接实现、人审 Diff 就行。

审过几轮「看起来对、跑起来不对」的补丁之后，结论会反过来——

在 AI 时代，TDD 不是过时了，而是更必要。失败测试是 Agent 没法假装完成的合同。

Kent Beck 后来把这个组合叫过 superpower：人定规格，机器填实现。循环没变，变的是谁写实现、以及你如何防止它作弊。

本文按「为什么还要 TDD → 给 AI 用的红绿重构 → 三层约束怎么落地 → 常见作弊 → 多 Agent 怎么拆」来写。工具用 Cursor、Claude Code 或 omp 都可以；工具选择不如循环纪律重要。 选手差异可对照前文 2026 流行 Coding Agent 能力对比。

一、为什么 vibe coding 过不了关

默认让 AI「实现这个功能」，它会同时写代码和测试。常见结果不是不会写，而是自己给自己出卷、自己批改：

症状 实际发生了什么
测的是实现细节 断言绑在私有函数、内部字段上，重构即红
断言太弱 assert True、只检查「没抛异常」
红了就改测试 合同跟着坏实现走，规格作废
过 mock 刷绿 测的是自己的 stub，不是真实行为

代码可以读起来正确而实际错误；从红到绿的测试，是 Agent 每轮都能自己核对、且不必你盯着的完成定义。

所以问题不是「还要不要 TDD」，而是：

以前：我先写失败测试，再写刚好让它通过的代码。
现在：我把同一件事做成 Agent 的工作协议——不准同一条链路又写规格、又当被告、又当裁判。

这和 Paperclip 里「你是董事会、Autonomy 是授予的特权」是同一类治理：日常可以让 Agent 跑，合同不能让它单方面改。

二、给 AI 用的 Red / Green / Refactor

三色循环没变。角色变了：

对人，TDD 靠习惯；对模型，靠阶段边界。训练目标是「把任务做完」。你说「写订阅接口的测试」，它听到的往往是「写测试然后把实现也做了」。不划边界，Red 会被一次性吞掉。

阶段 人做什么 AI 做什么 完成标准
Red 写清行为、边界、错误路径 只写测试，不写实现 因「行为不存在」而失败，不是 import / 文件名 typo
Green 审测试、冻结断言 最小实现让测试过 不准改测试来凑绿
Refactor 抽查设计 在绿灯下整理结构 对外行为不变，测试仍绿

人的杠杆在 规格和门禁，不在手写每一行实现。Red 阶段那一眼——失败信息是不是在描述你要的行为——比事后读 400 行实现值钱。

三、三层约束：口头嘱咐不够

「请用 TDD」几乎总会被任务完成欲冲掉。要叠三层，一层比一层硬。

3.1 Prompt：一次只做一个阶段

Red：

Green：

Refactor：

两个词比一段方法论管用：只写测试，以及 **Stop.**（或「先别实现」）。

更稳的一招：Red 确认后，先把测试提交进 git，再让 Agent 实现。 测试进历史后，改断言会变成显眼 Diff，作弊成本立刻升高。

3.2 项目规则：写进仓库，而不是每次重说

Cursor 用 .cursor/rules；Claude Code 用 CLAUDE.md。规则解决「记得做」；下一节的 Hook 才解决「不做就不让停」。

需要可发现、可复用时，把同一套流程收进 Skill，而不是把整篇方法论塞进系统提示。写法见 Agent Skills 编写最佳实践：description 写清何时触发，正文保持精简，细节往外拆。

3.3 机械闸门：Hook 比记忆可靠

规则是软的。Agent 赶着收工时，软约束会蒸发。Claude Code 可以把纪律做成脚本：

闸门 时机 作用
PostToolUse 改完文件 自动跑相关测试，把失败喂回模型
Stop 本轮要结束时 测试仍红就不许停（exit 2）
PreToolUse / TDD Guard 写实现前 没有先红就落地生产代码，直接拦

社区里常见的是 tdd-guard、tdd-guardian 这类插件：提交 / 推送前检查单测、集成、覆盖率，甚至 mutation。不必从第一天就上全套；先做到「红的时候不准宣布完成」，已经比口头 TDD 强一个数量级。

Cursor 强在审 Diff：Red 和 Refactor 适合你点一下再接受；Green 循环会稍慢，适合「大块实现、认真看 Diff」。同一条纪律，终端 Agent 更适合把跑测试接进循环，IDE Agent 更适合把合同审清楚。上下文为什么不能靠「把聊天记录一股脑塞回去」，见 Cursor 与 Claude Code 的上下文工程——测试输出要进上下文，但应是短失败摘要，不是整份日志。

omp 若开了 Advisor，也可以把「有没有先红、有没有改测试凑绿」写成旁观评审的 blocker，而不是等你事后翻 Diff。

四、人还是要盯的四种假绿

AI-TDD 最容易在这些地方假装成功。Red 之后、合并之前，值得停一下的就这四件：

  1. 假红：失败是 import 错了、文件名错了、测试没收集到，不是行为不存在。
  2. 空测试：assert True、只检查「函数能调用」，没有断言业务结果。
  3. 过 mock：把依赖全假掉，测的是自己的 stub。
  4. 改规格凑实现：红了就改 expect，合同作废。

一条经验规则：失败信息里应出现你在规格里写过的词（例如「余额不足」「拒绝下单」），而不是 ModuleNotFoundError。

覆盖率是辅助，不是合同。高覆盖率的空断言仍然是空的。更狠的检查是 mutation：改一行生产代码，测试该红不红，说明断言没咬住行为。核心路径值得做；原型阶段不必。

五、多 Agent 时，把 TDD 做成组织协议

单会话里靠 Stop；多 Agent 里靠分工。测写与实现拆开之后，Implementer 根本看不到「请放宽断言」这种诱惑。

任务拆解也要带着「为什么」：使命 → 项目目标 → Agent 目标 → 票。票上的验收条件就是测试用例，而不是一段散文需求。Heartbeats 和预算管的是「别空转」；TDD 管的是「干完的定义可执行」。

这不是把公司开大，而是把同一条红绿循环，从一次对话升级成可审计的流水线。

六、什么时候用，什么时候别用

代价真实：循环比 vibe coding 慢；Agent 会想改测试。换来的是完成定义可执行、可重复、可交给下一只 Agent。

值得上： 业务规则、API 契约、钱 / 权限 / 状态机、回归高发的核心路径。

不必硬上： 一次性脚本、还在找感觉的原型、以视觉为主的 UI（改用截图或浏览器走查）。

一句话：规格已经清楚、做错代价高，就走 TDD；规格还在漂，先允许探索，收口时再把行为冻成测试。

七、一条可直接复制的会话协议

对 Cursor / Claude Code / omp 说：

我们按 TDD 做「用户余额不足时拒绝下单」。

第一轮：只写失败测试（含成功下单、余额不足；若相关再加并发扣减）。不要写实现。跑测试，把失败输出贴给我。Stop。

我确认测试后，你再最小实现，禁止改测试。直到绿。然后再重构。

把这段收进 Rule 或 Skill 之后，日常就不用每次从零解释 TDD。你只需要补上这一次的行为列表。

八、小结

AI 不会让 TDD 过时，它让「没有可执行完成定义」这件事变得更贵。

压成四句就够用：

  1. 失败测试是合同，不是实现的附属品。
  2. 一次只做一个颜色，Stop 是边界，不是礼貌。
  3. 口头不够，规则不够，闸门才硬。
  4. 测写与实现拆开，合同才不会被同一只 Agent 改掉。

你不是在教模型「什么是 TDD」。你是在给它一套不能绕开的工作协议：先红，后绿，再重构；绿了才叫做完。
