一、入门

概览

omp 是什么

omp（读作“oh-em-pi”，二进制文件为 omp）是 Mario Zechner 的 Pi 的一个分支。它以单个 Bun 进程运行，可驱动你拥有凭据的任何模型提供商，并提供扁平化工具接口，供模型读取代码、运行命令、编辑文件、驱动调试器，以及生成可通过进程内 IRC 总线协调的子代理。

会话会以 JSONL 格式持久化到 ~/.omp/agent/sessions/。你可以恢复、派生、创建分支并分享它们。设置、凭据、插件和缓存均位于 ~/.omp/agent/。除非你调用会向外通信的工具，否则不会有任何数据离开本机。

初次使用？可跳转至 快速开始 了解安装和首次提示，或阅读 使用 omp 了解交互模式的组成。

面向谁

面向长期使用终端、跨多个仓库工作，并希望编码代理具备与自己相同能力的工程师：read、search、调试器、LSP、子进程、GitHub。omp 默认克制，且处处可配置——任何行为变更都只需一个配置文件（~/.omp/agent/config.yml）、一个 CLI 参数或一条斜杠命令。

独特之处

像 git 一样为会话创建分支
每个会话都是一个 JSONL 文件。/branch 可从同一文件中的任意历史消息创建新叶节点；/fork 会生成新文件。/tree 可遍历它们。可通过 CLI 的 omp -c 或 omp -r 恢复会话。

能够相互私信的子代理
task 工具将工作分发给子 omp 进程。同级代理可在 IRC 对等列表中看到彼此，并直接交换消息——无需经由父代理往返。

具备过期锚点恢复能力的哈希行编辑
每一行都带有简短的内容哈希锚点。模型通过锚点编辑，无需复现空白字符；在文件损坏前即可捕获过期锚点。

进程内 LSP 与 DAP
lsp 可执行重命名、查找引用、代码操作、诊断和悬停。 debug 工具封装了 DAP，支持通过内置适配器（gdb、lldb-dap、debugpy、dlv、js-debug-adapter 等）设置断点、单步执行和查看局部变量。

将 GitHub 视作虚拟文件系统
read pr://1428、read issue://1234、read pr://1428/diff/3。Issue、PR 和差异均是虚拟 Markdown，代理使用与读取本地文件相同的 read 工具读取它们。

接入任意提供商
可通过 OAuth 登录 Claude Pro/Max、ChatGPT、Copilot、Cursor、Z.AI 等，也可在环境中设置 API 密钥。按角色划分的模型（default、smol、slow、plan）会根据你已验证的身份自动解析。

计划模式
/plan 会针对独立的规划模型，在沙盒中执行一次规划轮次。批准后可选择：执行并清除、保留记录，或压缩上下文。

约定

  • 二进制文件是 omp。包为 @oh-my-pi/pi-coding-agent。代理目录为 ~/.omp/agent/；设置位于 ~/.omp/agent/config.yml；凭据位于 ~/.omp/agent/agent.db。
  • 斜杠命令写作 /plan，在活跃会话内运行。
  • CLI 参数使用长格式（--resume）；存在短别名时会在 CLI 页面列出。
  • 设置键是 config.yml 中的点分路径，例如 memory.backend。
  • 内部 URL 使用 scheme:// 格式，并通过 read 工具解析：pr://、issue://、skill://、artifact://、memory://。

使用 omp

交互式会话的组成

直接运行 omp 会打开交互式会话。界面从上到下分为四个区域：

标题栏
首次启动显示 OMP 标志；对话开始后显示紧凑的会话标题栏：标题、会话树中的当前分支，以及任意活动模式横幅（计划、循环、目标）。

消息区
用户提示、助手轮次和工具调用卡片。每次工具调用显示为一行摘要；按 Ctrl+O 可展开卡片，查看完整输出、完整差异或完整 bash 记录。

编辑器
支持多行输入、文件引用、路径补全、粘贴图片、shell 转义和交接给外部编辑器。

页脚
两行淡显文字（扩展发布状态时为三行）。第一行：工作目录和当前 git 分支。第二行：token 计数、成本、上下文使用量和活动模型。

消息队列

代理工作时仍可输入，消息不会丢失。轮次进行中提交的消息会排队，并通过两条通道依次处理。

组合键 通道 送达时机
Enter 引导消息 当前助手轮次完成工具调用后。用于在执行中修正方向。
Ctrl+Q / Ctrl+Enter 后续消息 代理完成所有排队工作并交出控制权后。用于“接着做这个”。
Escape — 中止活动轮次。排队的引导和后续消息会恢复到编辑器栈，而非丢弃。
Alt+Up — 将最近排队的消息重新放回编辑器。

以下三个设置决定行为，可在 /settings → 交互 下配置，或作为 ~/.omp/agent/config.yml 中的顶级键：

  • steeringMode — all 或 one-at-a-time（默认）。
  • followUpMode — all 或 one-at-a-time（默认）。
  • interruptMode — immediate（默认）或 wait。

模式

交互模式是默认模式。其他模式是通过 --print 或 --mode <mode> 选择的非交互界面。

模式 调用方式 输出 用途
交互式（默认） omp TUI 日常工作。
Print omp -p "prompt" 标准输出中的纯文本，无 TUI。 脚本、CI、shell 管道。
JSON omp --mode json -p "prompt" 标准输出中的换行分隔 JSON 事件。 稳定地管道传给其他工具。
RPC omp --mode rpc 通过 stdio 的 JSON-RPC。 SDK 和编程客户端。参阅 RPC 模式。
ACP omp --mode acp（或 omp acp） 通过 stdio 的 Agent Client Protocol。 编辑器和其他支持 ACP 的宿主。参阅 ACP。

--mode rpc-ui 是 rpc 的一种变体，会将 TUI 内工具调用界面呈现给客户端。完整参数清单请参阅 CLI 页面。

计划模式

对于涉及多个文件或顺序并不明显的修改，请使用计划模式。/plan 会针对独立规划模型，在沙盒中执行只读规划轮次（只能写入其计划文件）；批准后，可选择执行并清除、保留记录或压缩上下文。完整说明见计划模式页面。

二、会话与日常操作

会话

会话

会话是磁盘上位于 ~/.omp/agent/sessions/ 下的仅追加树，按工作目录分组，因此两个项目绝不会共享历史。每个轮次都是带父指针的节点；创建分支会移动叶节点并从该处继续追加，因此原始时间线始终保留在文件中。磁盘格式请参阅会话格式。

会话 ID 是按时间排序的 UUID（v7），因此会按创建时间排序，使用短 ID 前缀即可通过 -r 标识会话。

恢复会话

四个参数覆盖常见场景：

-c 优先使用每个终端的面包屑，因此同一目录中的分屏和 tmux 窗口不会互相干扰。若面包屑缺失，则回退到 cwd 中最新的会话，再启动新会话。

-r <prefix> 会先在当前项目中查找 ID，然后全局查找。如果匹配项位于其他位置，omp 会提示将其派生至当前 cwd，而不会悄悄替你切换目录。--session 是 --resume 的别名。

浏览树（/tree）

/tree 是原地导航器。它可将叶指针移至当前文件中任意较早的消息——不会创建文件，也不会派生——适合某个轮次偏离方向，或需要跳过冗长的工具调用时使用。

  • 输入内容可模糊搜索所有消息；←/→ 可在结果间翻页。
  • Ctrl+O 可循环切换过滤器：默认 → 无工具 → 仅用户 → 仅已标记 → _全部_。
  • Shift+L 可为高亮条目添加标签。已标记条目会出现在选择器中并在压缩后保留，因此适合作为“稍后回到这里”的标记。

导出

/export [path] 会将当前会话写为自包含 HTML 渲染——包含标题、条目、系统提示和工具模式——并在浏览器中打开。omp --export <session.jsonl> [output] 也可在不启动交互式会话的情况下完成相同操作，适合批量渲染归档文件。

/dump 将纯文本记录复制到剪贴板：系统提示、活动模型、工具定义、每条消息和工具结果。/copy 会打开较小片段的选择器——最后一条代理消息、单独的代码块，以及代理最近运行的命令。

批准并执行

文件操作

文件操作

所有文件操作流程都使用五种内置工具之一。read 读取字节（支持行范围、归档成员和 URL 获取），write 创建或覆盖整个文件，edit 应用按行锚定的补丁，find 解析路径 glob，search 执行正则内容查找。结构化改写和合并冲突请参见结构化编辑；符号感知的重命名请参见代码智能。

read

单个 path 参数可处理磁盘文件、目录、归档、SQLite 数据库、PDF、Office 文档、Jupyter Notebook、图像和普通 Web URL。相同参数也可解析内部 scheme：skill://、pr://、issue://、agent://、artifact://、history://、memory://、mcp://、local://、rule://、vault://、conflict://。

在路径后附加带有 : 的选择器以限定读取范围。:50-200 表示行范围，:50+150 表示计数形式，:raw 绕过摘要，:conflicts 为合并冲突块建立索引。输出带有 [path#TAG] 快照头和编号行（41:text），因此 edit 可以在之后引用精确行。对可解析源代码使用裸路径时，返回结构摘要——保留签名，省略函数体。需要函数体时，请使用范围选择器或 :raw 再次读取。

write

write 创建新文件或整体替换现有文件。分发逻辑与 read 相同：archive.ext:inner/path 写入归档内部，db.sqlite:table 插入一行，db.sqlite:table:key 更新或删除一行。生成的文件会受到保护以防意外覆盖；格式化保存流程会在字节写入磁盘前执行。

当文件已经存在且只需修改其中一部分时，请改用 edit。整体改写会丢失锚点历史，并使 diff 审查更嘈杂。

edit

edit 会应用由每会话快照存储验证的按行锚定补丁。模型读取一个片段，将读取输出中的 [path#TAG] 头复制过来——四位十六进制标签会标识整个文件——再针对普通行号生成操作。如果自读取后文件发生变化——可能来自另一代理、格式化器或手动保存——标签将不再匹配，补丁会被恢复或拒绝，而不会错误覆盖其他行。修复方式始终相同：重新 read 该片段，并针对新标签生成新补丁。

补丁语法（默认变体 hashline）是一个包含一个或多个文件段的 input 字符串。每个段均以 [PATH#TAG] 开头；操作使用普通行号。载荷行以 + 开头。

操作 效果
replace N..M: 使用载荷行替换包含端点在内的行范围。
replace block N: 替换从第 N 行开始的整个语法块（由 tree-sitter 解析）。
delete N..M 删除包含端点在内的行范围，不带载荷。
insert after N: / insert before N: 在第 N 行后/前插入载荷行（insert head: / insert tail: 作用于文件两端）。

可通过 PI_EDIT_VARIANT 环境变量按会话覆盖该语法；可接受的值为 hashline（默认）、patch、apply_patch 和 replace。~/.omp/agent/config.yml 中对应的 edit.mode 设置可进行持久化配置。

当修改属于结构性操作——重命名符号、替换 API 形状、改写每个调用点——请使用 ast_edit 或 lsp rename。两者都会忽略空白，并能适应会导致按行锚定补丁失效的格式变动。

find

find 解析路径 glob。通过 paths 传入一个或多个模式；结果为相对于 cwd 的换行分隔路径，按 mtime 排序（最新优先）。默认遵守 .gitignore。用它进行枚举而不读取内容：与 search 的拆分是刻意设计的，以避免模型意外将所有匹配文件加载到上下文中。

search

search 会在文件、目录、glob 或内部 URL 的内容中执行正则匹配。匹配结果以带锚点前缀的行返回（*5th|content）；上下文行以前导空格表示。遵守 .gitignore。当正则包含字面量 \n 时，会自动启用跨行模式。原生引擎支持分页——使用 skip 可越过早先匹配项，无需重新扫描。

仅需路径列表时使用 find，需要查看匹配内容时使用 search。如需忽略空白和注释的结构化匹配，请在结构化编辑页面使用 ast_grep。

结构化编辑

结构化编辑

按行锚定的 edit 补丁很精确，但在重新格式化后容易失效。结构化编辑则直接操作 AST：同一模式可匹配 foo( x )、foo(x) 和 foo(/* comment */ x)。对于需要触及每个导入方的符号感知重命名（以 TypeScript 为主、由语言服务器支持），请使用 lsp rename——它能理解作用域和重导出，这是 ast-grep 做不到的。

ast_edit

ast_edit 使用 ast-grep 对代码进行结构化改写。每个操作是 { pat, out }：pat 匹配 AST 形状，out 是替换模板。模式匹配的是结构而非文本，因此会忽略空白和注释。

元变量 匹配内容
$A 一个 AST 节点，并捕获为供模板使用的 $A。
$_ 一个 AST 节点，不捕获。
$$$ARGS 零个或多个节点，并捕获为供模板使用的 $$$ARGS。
$$$ 零个或多个节点，不捕获。

复用同一个元变量会强制要求内容相同：$A == $A 能匹配 x == x，但不能匹配 x == y。语言根据 paths 中的文件扩展名推断；为保证改写结果确定，应将每次调用限定为一种语言。

每次 ast_edit 运行都会先暂存为预览。TUI 会显示 diff 和替换次数；只有模型调用带有 { action: "apply" } 的 resolve 后才会写入磁盘（见下文）。使用 astEdit.enabled 控制该工具；启用后，它会与 edit 一同自动启用。

一次性的本地文本编辑请优先使用 edit。只读的结构化搜索请使用 ast_grep：它使用相同的模式语法但不改写，返回带锚点前缀的匹配行，并内联元变量捕获结果。

conflict://

当文件包含 Git 合并标记时，read 会将每个 <<<<<<< / ======= / >>>>>>> 块注册为虚拟 URL conflict://N。代理选择一方并写回，内容会在原位置被替换。

URL 效果
conflict://N 文件中的第 N 个冲突块。向其写入内容即可替换该块。
conflict://* 批量形式；使用相同内容或简写解决所有冲突块。
read path:conflicts 列出 path 中每个未解决冲突的索引，每块一行。

简写 @ours、@theirs 和 @base 分别代表合并的三个版本。当整个块都应采用某一侧时，一行 @theirs 就是完整编辑。

无需合并 UI，也没有专用工具。同一组 read 和 write 即可处理整个流程。

resolve

resolve 用于完成待处理操作。会暂存变更的工具（ast_edit、扩展提供的预览、计划审批）会将回调加入队列；在任何内容写入前，必须应用或丢弃该回调。其约定为 { action: "apply" | "discard", reason }；生产者的回调会运行，其结果成为工具响应。

在没有待处理操作时调用 resolve 会报错，因此代理不会意外接受上一轮遗留的预览。丢弃操作一次调用即完成且具备原子性；不支持部分应用。

应在何时使用哪种方式

ast_edit
跨多个文件改写某种语法形状：重命名调用、替换 API、删除匹配的语句。不受格式影响。

lsp rename
跨所有导入方进行符号感知重命名，并遵循作用域和重导出。当 ast-grep 的文本形状匹配可能捕获到另一模块中同名符号时，应使用它。

conflict://
解决合并冲突。读取以枚举，写入以替换，重复直到文件不再含有标记。

resolve
接受或拒绝任何已暂存的预览。它是 ast_edit、计划审批和自定义工具预览共用的约定。

edit
针对刚读取的特定片段执行按行锚定补丁。适用于局部改动且周边文本稳定的情况。

代码智能（LSP）

通过语言服务器重命名

正则重命名会遗漏重导出、被遮蔽的局部变量和通过字符串键进行的访问。lsp action=rename 会请求服务器生成 WorkspaceEdit，并以原子方式应用到所有受影响的文件。若服务器拒绝（符号不可重命名，或某项编辑会发生冲突），则不会写入任何内容。rename_file 也遵循相同原则：移动文件时会一并改写导入。

对于不涉及符号的其他结构化改写——基于语法模式的 codemod、大规模机械重构——请参阅结构化编辑。

task 工具

task 可并行启动一个或多个子 agent。tasks 中的每一项都会获得独立的 assignment 字符串（以及该批次共享的 context），并在自己的子会话中运行。并发数由信号量限制；每个 agent 一有结果便会交付（异步执行关闭时则内联交付）。每个 agent 的完整输出始终可通过 agent://<id> 访问，其会话记录可通过 history://<id> 访问，父 agent 随时可用 read 读取。

并行机制

单次 task 调用中的所有任务都会同时启动，并独立运行。每个子 agent 都会在其 IRC 对等方块中看到其他任务，因此它们可在工作期间互相交流。任务完成后会进入 idle（TTL 到期后进入 parked）——其 ID 仍可通过 IRC 寻址，向它发送消息会将其唤醒以执行后续回合。

IRC 在线状态

irc 工具在同一进程中的 agent 之间传递简短的文字消息。主 agent 是 Main；子 agent 使用其任务 ID，例如 AuthMap（名称重复时为 AuthMap-2）。

  • op: "list" 列出对等方及其状态（running/idle/parked）和未读消息数。
  • op: "send" 向 to（对等方 ID 或 "all"）发送 message，并立即返回投递回执——它永不等待接收者。传入 await: true 可阻塞至该对等方回复。
  • op: "wait" 阻塞等待传入消息；op: "inbox" 会取出待处理消息。

没有开关设置：只要有可发送消息的对象，irc 就可用——所有子 agent 中均可用，任何仍可启动子 agent 的会话中也可用。

向已完成的对等方发私信

已完成的子 agent 不会消失：它们会进入 idle，TTL 后进入 parked，始终可被寻址。向空闲或停驻的对等方发送私信会将其唤醒（或复活）并把消息作为后续回合执行。向忙碌对等方发送私信会在其下一个步骤边界作为旁注注入；若使用 await: true 发送，而该对等方无法及时到达步骤边界，则它会通过旁路自动生成简短回复。

  1. 对等方 B 调用 irc op=send to=A await=true，并阻塞等待回复。
  2. 若 A 正在工作，消息会在 A 的下一个步骤边界送达（或触发自动回复路径）；若 A 处于空闲或停驻状态，私信会将其唤醒。
  3. B 收到 A 的回答后继续执行。

若在超时前未收到回复，请再次检查 inbox 或 wait，而不要重新发送——对等方可能会在完成当前步骤后回复。

TTSR 规则

工作原理

TTSR 规则是带有 frontmatter 的 Markdown 文件。omp 在字节到达时，以每条规则的 condition 正则表达式监视实时模型流。首次匹配会中止生成，将规则正文作为 system reminder 前置，然后重试相同请求——匹配点之后被中止的续写不会消耗 token。

默认情况下，每条规则在每个会话中最多触发一次（ttsr.repeatMode: after-gap 使其可在配置数量的回合后重新启用）；已触发的规则会随会话持久化，因此恢复会话后，已消耗的规则仍保持已消耗状态。当某类错误只在模型流式生成期间出现时使用 TTSR——例如调用被禁用的 API、生成你希望压缩的样板代码，或错误命名项目特有约定。

对于限定在工具调用范围内的规则，可设置 interruptMode: never，将提醒作为 <system-reminder> payload 合并到匹配工具的 toolResult 中，而不是中止流。模型会在下一回合看到修正；这适用于不希望承担中止/重试成本的轻度提醒。

规则存放位置

  • .omp/rules/<rule>.md — 项目范围，随仓库提交
  • ~/.omp/agent/rules/<rule>.md — 用户范围，应用于所有位置

同名时，项目规则覆盖用户规则。

解析顺序

omp 需要某个提供商的凭据时，会遍历以下列表并返回首个命中项：

  1. omp 进程上的 --api-key 运行时覆盖。
  2. agent.db 中保存的 API 密钥。同一提供商保存多个密钥时，调用会轮询分配。
  3. agent.db 中保存的 OAuth 凭据，在每次调用前按需刷新。
  4. 提供商环境变量（ANTHROPIC_API_KEY、OPENAI_API_KEY、GEMINI_API_KEY、ZAI_API_KEY 等）。
  5. models.yml 中的 apiKey: 字段。先将其视为环境变量名称检查，随后将其视为字面 token。

同一提供商同时存在 API 密钥和 OAuth 凭据时，API 密钥优先。显式设置 ANTHROPIC_OAUTH_TOKEN 可强制 OAuth 优先。

环境变量

解析顺序

omp 通过分层的 .env 链解析环境变量。最先定义某键的来源生效：

  1. 已有的进程环境变量。
  2. $PWD/.env — 启动 omp 时所在目录下的项目 .env。
  3. ~/.omp/agent/.env — 或在设置了相应变量时的 $PI_CODING_AGENT_DIR/.env / $PI_CONFIG_DIR/agent/.env。
  4. ~/.omp/.env — 遵循 PI_CONFIG_DIR。
  5. ~/.env — 用户主目录下的 .env。

在每个 .env 文件中，写作 OMP_FOO 的键会镜像为 PI_FOO，因此旧版 OMP_* 配置无需改名仍可用。~/.omp/agent/config.yml 中的设置覆盖内置默认值；CLI 标志再覆盖两者。标志列表见 CLI 参考。

环境变量在启动时读取。编辑 ~/.env 或项目 .env 后，请重启 omp。

凡以 _API_KEY、_TOKEN 或 _OAUTH_TOKEN 结尾的一律视为密钥。切勿提交 .env；切勿粘贴到聊天记录。含凭据的 .env 请 chmod 600。

.env 文件格式

每行一条 KEY=value，# 为注释；值含空格或 shell 元字符时建议加引号。不支持插值，也不需要 export 关键字。

设置

存放位置

持久化设置位于 ~/.omp/agent/config.yml（可通过 PI_CODING_AGENT_DIR 覆盖父目录，或通过 PI_CONFIG_DIR 重命名配置根目录）。该文件是普通 YAML 树；缺失的键会回退到内置默认值。

可通过三种方式编辑：

  • 会话内使用 /settings —— 菜单式操作，保存时进行验证。
  • 在 shell 中使用 omp config <action> —— 适用于脚本化编辑，参见 CLI 参考。
  • 使用文本编辑器 —— 下次启动时重新读取；格式错误的 YAML 会让 omp 记录警告并忽略整个文件，因此编辑后请进行验证。

优先级

从最高到最低：

  1. CLI 参数（--slow、--no-pty、--api-key，……）
  2. 环境变量（PI_SLOW_MODEL、ANTHROPIC_API_KEY，……）
  3. ~/.omp/agent/config.yml
  4. 内置默认值

由 /login 保存的 OAuth 凭据与 config.yml 一同存放在 agent.db 中，并遵循相同的查找顺序：对于同一提供商，数据库中的令牌优先于环境变量。

RULES.md 固定规则——作为始终应用的规则加载，其完整文本会注入系统提示词。 每个请求都会存在，而不仅是会话启动时。

放置位置

项目文件会从当前工作目录向上遍历至仓库根目录（仓库外则至主目录），因此任意祖先检出根目录都可能被读取。全局文件位于 ~/.omp/agent/ 下，应用于每个会话。

也会发现相邻的其他代理框架文件：Codex AGENTS.md、Claude CLAUDE.md、Cursor 规则、.clinerules、Copilot 指令和 opencode 上下文文件。每个已加载条目都会在/extensions中显示其来源路径。

解析顺序

存在多个 AGENTS.md 时，omp 按由泛至具体的顺序拼接：

  1. 全局 —— ~/.omp/agent/AGENTS.md
  2. 项目祖先目录 —— 从 cwd 向上遍历找到的每个 AGENTS.md，最远的在前
  3. 从 cwd 向上遍历找到的最近 .omp/AGENTS.md

SYSTEM.md 和 APPEND_SYSTEM.md 只应用一个文件：最近的项目文件会优先于全局文件，而不是与其拼接。RULES.md 则同时应用两个作用域——存在时，全局 ~/.omp/agent/RULES.md 和最近项目 .omp/RULES.md 都会被加载为始终应用的规则。

AGENTS.md 的实际用法

将 AGENTS.md 视为代理的 README：约定、构建命令、容易被忽略却至关重要的文件，以及它应默认使用的目录布局。代理只会在会话启动时读取一次，因此应保持精简——过长的文件会在每轮消耗上下文。

RULES.md 与固定行为

需要持续强制执行的指令应写在 RULES.md 中。omp 将它加载为始终应用的规则，并把完整内容注入系统提示词，因此即使经过多轮对话，它仍会随每个请求一同传递。它适用于硬性约束（“绝不提交密钥”“交付前始终运行 just test”），不适合一般说明——后者应写在 AGENTS.md 中。

替换系统提示词

SYSTEM.md 会整体替换内置系统提示词。你会失去 omp 自带的精心调优指令，包括工具使用指导。除非确实想要不同的代理人格，否则优先使用 APPEND_SYSTEM.md。

Skills

什么是技能

技能是位于具名目录下的 Markdown 操作手册。只有其 frontmatter 的 description 会保留在系统提示词中。模型会根据当前任务与该描述的匹配结果加载正文，或者你也可以通过 /skill:<name> 调用它。较长的操作手册在需要前不会消耗上下文。

目录结构

发现过程不递归——skills/ 下每个直接子目录对应一个技能。技能目录内的同级文件可由模型通过 skill://<name>/path/to/file.md 访问。

Frontmatter

字段 必填 作用
name 否 技能标识符；默认为目录名。用于 /skill:<name> 和 skill://<name> URL。
description 是 技能加载前模型唯一可见的部分。应包含具体的动词、名词和范围。
hide 否 使技能仍可通过 skill://<name> 和 /skill:<name> 加载，但不在系统提示词的列表中显示。

完整的 SKILL.md

编写能触发加载的描述

模型选择技能的方式与选择工具相同：它会将任务与描述文本匹配。模糊的描述会被跳过；具体的描述会被加载。请写明动词（编写、审查、调试）、名词（Postgres 查询、Lambda 错误、快照测试），并在适用时注明范围（src/parser/、*.test.ts）。

不佳：‘Helps with database stuff.’ 良好：‘Writing, reviewing, or optimizing Postgres queries, schemas, or configs.’ 不佳：‘Tests.’
良好：‘Adding or extending Vitest tests for the importer module; covers fixtures, snapshot tests, and integration setup.’

对于应当始终加载的技能（项目约定、强制检查），仍应保持描述具体；然后在首个提示中使用 /skill:<name> 显式调用，而不是依赖匹配结果。

提示词模板

两种形式

提示模板是一种斜杠命令。去掉扩展名后的文件名即为命令名称。最简单的形式是一个包含提示正文的 Markdown 文件；若需要参数解析、自定义 UI 或后台工作，则应使用 TypeScript 模块。

存放位置

项目命令会覆盖同名的全局命令。运行 omp -p '/extensions' 可查看已加载内容。

Markdown 模板

Markdown 命令由 YAML frontmatter 与提示正文构成。调用命令时，正文会成为用户消息。位置参数为 $1、$2、…；拼接后的剩余参数为 $@ 或 $ARGUMENTS。

使用 /review-pr 482 --focus security 调用它。$1 解析为 482，$@ 解析为 --focus security。

Frontmatter
字段 作用
description 在 / 自动补全中显示的单行摘要。若缺失，则回退到正文第一条非空行。
name 覆盖命令名称（适用于 .codex/OpenCode 风格命令文件；OMP 原生命令使用文件名）。

TypeScript 模块

需要解析参数、提示用户、运行 shell 命令或渲染自定义 UI 时，请改用 TS 模块。默认导出一个工厂函数，它接收自定义命令 API 并返回命令定义（或命令定义数组）。

工厂函数可以返回多个命令。从 execute 返回 undefined 表示命令已自行处理全部工作（不会发送提示）。如需自定义 UI、消息渲染器和键盘快捷键，请改为编写插件。有关相关的生命周期 API，请参阅钩子；若需要按需操作手册而非固定提示，请参阅技能。

调用

在交互模式中，所有模板都会显示在 / 自动补全选择器中。从 CLI 调用时，将斜杠命令作为提示传递：omp -p '/review-pr 482'。有关选择器、历史记录和内置命令参考，请参阅斜杠命令。

Hooks

钩子的位置

发现过程不递归：位于更深一层目录中的文件会被忽略。在 CLI 中，--hook <path> 会加载显式指定的文件（它是 --extension 的别名）。

可挂接的事件

接口 事件 返回约定
工具调用拦截 tool_call 返回 { block: true, reason } 可拒绝调用。reason 会成为模型看到的错误。第一个阻止结果生效。
工具结果改写 tool_result 返回 { content?, details?, isError? } 可修改模型接收到的内容。处理器会串联执行。

第一个 block 结果生效——多个前置钩子之间的顺序由文件系统稳定决定，但应将正则表达式视作最后一道防线，而不是唯一防线。

对工具输出中的密钥脱敏

这是一个后置工具钩子，它会改写 read 结果，在模型看到之前清除 API 密钥。

调试钩子

运行 omp -p '/extensions'，确认钩子是否已加载及其路径。若未加载，说明文件不在可发现目录中——将其移至 ~/.omp/agent/hooks/pre/ 或 .omp/hooks/pre/，或者使用 --hook /path/to/file.ts 显式加载。有关相邻的定制接口，请参阅提示模板和技能；若希望每轮注入静态规则而非使用活动拦截，请参阅上下文文件。

自定义工具

何时编写自定义工具

当模型需要完成项目专属的操作时，请使用自定义工具：查询内部 API、运行领域检查、修改远程系统。如果只是要接入现成的集成，请改用 MCP 服务器。

放置位置

将 TypeScript 模块放在以下任一位置：

  • ~/.omp/agent/tools/<name>/index.ts —— 用户作用域
  • .omp/tools/<name>/index.ts —— 项目作用域

也会发现 .claude/tools/ 和 .codex/tools/。工具注册名称来自工厂函数返回值中的 name 字段。同一目录中的普通 .md 和 .json 会被视为元数据，而非模块。

骨架

默认导出一个工厂函数。工厂会收到带有注入 Zod 实例（pi.zod）的主机 API（pi）；params 从 schema 获得静态类型。

工厂字段

字段 用途
name 模型调用的工具名。不得与内置工具或其他自定义工具冲突。
label TUI 中显示的易读标签。
description 模型决定是否调用时看到的描述。应明确说明触发条件。
parameters Zod schema（pi.zod；也接受 TypeBox 风格 schema）。用于校验并为 params 提供类型。
execute (toolCallId, params, onUpdate, ctx, signal) => Promise<ToolResult>。将 signal 传给子进程以传播取消操作。
renderCall / renderResult 可选。调用卡片和结果的自定义 TUI 渲染器。

流式输出

在 execute 内调用 onUpdate(partial)，可在最终返回前向 TUI 推送进度。模型只会看到最终的 content；onUpdate 面向用户。

返回结构

返回 AgentToolResult。content 是模型读取的内容；details 不会进入提示词。

text 块会成为内联上下文。image 块会传递给支持视觉的模型。

加载和冲突

加载时会拒绝名称冲突，包括与内置工具及任何已加载自定义工具的冲突。没有覆盖标志，内置工具始终优先。运行 omp -p '/extensions' 可查看已加载和被拒绝的内容。

MCP

何时使用 MCP

如果已有开发者发布了你所需集成的 MCP 服务器——文件系统、GitHub、Slack、Linear、Postgres——就应使用 MCP。只需加入 JSON 配置；omp 会处理握手、OAuth、重连和工具注册。如果需要定制逻辑，请改为编写自定义工具。

配置文件

omp 按以下优先级从各位置读取 mcp.json：

  • .omp/mcp.json — 项目级，由 omp 管理
  • ~/.omp/agent/mcp.json — 用户级，由 omp 管理
  • .claude/、.cursor/、.vscode/、.gemini/、.windsurf/、opencode.json — 自动发现
  • 仓库根目录的 mcp.json 或 .mcp.json — 独立回退配置，优先级最低

项目条目会覆盖具有相同键的用户条目。要禁用服务器而不删除其配置，请在用户文件（~/.omp/agent/mcp.json）的 disabledServers 中添加其键。

stdio 传输

启动本地进程。omp 通过其标准输入和标准输出传输 JSON-RPC。

设置了 command 时，type 默认为 "stdio"。加载时会在 command、args、env、cwd、url、headers、auth 和 oauth 中展开 ${VAR} 与 ${VAR:-default}。

可流式 HTTP 传输

连接远程端点。通过 headers 发送 bearer token，或通过 oauth 配置 OAuth。

对于 OAuth 服务器，请使用 /mcp reauth <name> 完成流程。凭据会保存到 agent.db（仅当前用户可读）；不会回写到 JSON。

发现与范围控制

工具显示为 mcp__<server>_<tool>。此前缀可区分两个拥有相同上游工具名称的服务器。连接、列出和加载工具会并行执行，并设有 250 ms 的快速启动门限——缓存的工具定义会立即作为延迟句柄显示，较慢的服务器则继续完成握手。每个服务器的故障相互隔离，传输会以退避策略自动重连。

按需激活

对于大型工具目录，将全部 MCP 工具载入提示词会浪费上下文。在 ~/.omp/agent/config.yml 中设置 tools.discoveryMode: mcp-only 后，MCP 工具会经过发现步骤：模型只会看到单一的 search_tool_bm25 工具，用它搜索所需能力，只有匹配工具才会被实例化到活动工具集中。默认的 auto 模式会在工具集超过 40 个工具后自动采取此方式。

插件

四个命令

命令 效果

来源

每个 omp install 来源都会解析为以下一种：

npm 包
omp install @scope/plugin-foo。裸名称和带作用域名称均可；支持 name@^1.2 形式的 semver 范围。

Git 仓库
omp install github:user/repo、omp install https://github.com/user/repo.git，或带引用的 Git URL：user/repo#tag。

本地路径
omp install ./path/to/plugin —— 适合开发插件时使用。omp 会为目录创建符号链接并监视其变更。

市场插件
先用 omp marketplace add <source> 添加目录，然后使用 omp install code-review@claude-plugins-official 这种 name@marketplace 格式。

市场目录

市场是一个 Git 仓库（或本地目录），其根目录包含 .claude-plugin/marketplace.json 目录。添加后，其中的插件可按短名称安装。

市场接口与 Claude Code 兼容，现有目录可直接使用。omp 内提供 /marketplace 和 /plugins 交互式等价操作；参见斜杠命令。

插件可打包的内容

插件根目录的布局与扩展目录保持一致。每个子目录均为可选。

安装时，omp 会将每个子目录合并到对应的发现入口。插件的 mcp.json 会增加 mcpServers 条目，themes/ 目录会增加主题文件，其他内容同理。卸载会撤销全部变更。

打包功能快速链接

  • 技能 —— 位于 skills/<name>/SKILL.md 的按需操作手册。
  • 提示词模板 —— 位于 commands/ 的 Markdown 斜杠命令。
  • 钩子 —— 位于 hooks/pre/ 和 hooks/post/ 的生命周期处理器。
  • 自定义工具 —— 位于 tools/<name>/index.ts、采用 TypeBox schema 的工具。
  • MCP 服务器 —— 通过插件 mcp.json 增加 mcpServers 条目。
  • 主题 —— 位于 themes/<name>.json 的调色板。

查看已加载内容

omp list 显示已安装插件；omp -p '/extensions' 显示每个功能面的视图——此会话中解析出的每个技能、命令、钩子、工具、MCP 服务器和主题，以及提供它的插件或目录。

安全性

插件可以注册在每次提示时运行的钩子、模型可无需确认调用的自定义工具，以及使用你的令牌与远程服务通信的 MCP 服务器。仅从可信来源安装插件——你实际上是在每轮运行任意 TypeScript。

安装前审计插件：克隆来源，阅读其 hooks/ 和 tools/，并略读 mcp.json。对未审查的代码，优先使用项目作用域安装（-l），并固定到特定 Git tag 或 npm 版本，而非跟踪 main。市场目录也同样如此——添加前先审查目录仓库。

记忆与压缩

记忆具有持久性：过去会话中的事实和约定会传递到新会话。它与压缩相邻但独立；压缩的作用是在上下文窗口内维持单个会话。

RPC 模式

启动

启动时，omp 会写入 {"type":"ready"}，然后从 stdin 每行读取一个 JSON 对象，并向 stdout 每行写入一个 JSON 对象。模式 flag 与其他 CLI 选项一同记录在 CLI 参考中。传入 --no-session 可避免此次运行写入 ~/.omp/agent/sessions/；省略它则会持久化，之后可通过与交互模式相同的通道恢复、派生或分支会话（Sessions）。

--mode rpc 是完全无头的。--mode rpc-ui 在相同协议上叠加 TUI 的交互表面：工具执行卡片、选择器和权限提示会以 extension_ui_request 帧到达，嵌入端必须以对应的 extension_ui_response 回应。

  • agent_start / agent_end — 回合边界。agent_end 带有单次 prompt 所等待的停止原因。

  • available_commands_update — 当前的斜杠命令表面；启动时发出一次，且命令元数据变更时再次发出。会话树转换（new_session / switch_session / branch）通过其命令响应观察。
  • extension_ui_request — 代理需要 UI：选择器、确认、输入或 OAuth URL。使用相同的 id 以 extension_ui_response 回应。工具执行卡片和权限提示仅在 --mode rpc-ui 下到达。

Shell 示例

输入一个 prompt，输出文本 delta，在 agent_end 时退出。无需语言绑定。

JSON 事件流模式

--mode json 是同一协议的打印模式变体。它从 argv（或 -p）接受一个 prompt，将相同的事件对象写到 stdout 后退出。可用于 CI 捕获、golden-file 测试，或将内容管道传给 HTML 导出器，而无需保持子进程存活。

帧格式、事件类型和渲染器均相同。差异仅在生命周期：--mode rpc 是可持续输入的长时间运行管道；--mode json 是一个 prompt、一个事件流，然后退出。

ACP

启动

该模式 flag 与其他 flag 一并列在 CLI 参考中。ACP 通过 stdio 使用 JSON-RPC 帧——将 omp 作为子进程启动，并将其 stdin/stdout 连接到你的客户端。

规范：zed-industries/agent-client-protocol。Zed 提供第一方 ACP 支持；其他实现该协议的编辑器也可以用同样方式驱动 omp。

初始化

ACP 不要求在启动时配置模型。客户端依次驱动 initialize、authenticate，然后才选择模型。当客户端选择 clientCapabilities.auth.terminal 时，omp 会声明 terminal 认证方法，并启动 omp TUI 以登录；否则仅提供 agent 方法——复用已经在 ~/.omp 下配置的提供商密钥和 OAuth 状态。

客户端所见内容

若客户端在 initialize 时声明文件系统和终端能力，代理会通过客户端路由内置工具 I/O。读取操作可看到未保存的缓冲区；写入操作会经由编辑器落盘。

omp 工具 ACP 方法
read fs/read_text_file
write fs/write_text_file
bash terminal/create + terminal/output（每次调用均使用客户端侧终端）

当客户端支持时，bash 调用和破坏性 edit 操作（删除和移动文件）受 session/request_permission 保护。代理会按工具在会话生命周期内缓存 allow_always 与 reject_always，因此一次批准即可覆盖长时间的编辑循环。系统会声明计划模式，使客户端可从其 UI 将代理切换至仅提议执行；工具调用更新携带 tool_call_update.locations，以便编辑器实时跟踪多文件编辑。

斜杠命令

大多数斜杠命令都会通过 ACP 命令列表公开，因此用户可在编辑器内使用同样的 /plan、/model、/compact 等命令。没有文本处理器、仅用于驱动 TUI 表面的命令会被过滤；/login 和 /quit 也会隐藏（登录由 ACP 的 authenticate 步骤负责；退出由客户端负责）。

文件引用（@path）和工具调用卡片与 TUI 中的行为相同——编辑器使用 ACP 的内容块类型渲染它们。

模式与配置更新

session/set_mode 和 session/set_session_config_option("mode", …) 都会发出 current_mode_update，以保持编辑器同步。/model 在切换后发出 config_option_update。

--auto-approve, --yolo 自动批准所有工具调用（跳过审批提示）。
--hide-thinking 在 TUI 输出中隐藏思考块。仅影响显示——不会禁用模型思考。
--help, -h 输出帮助及环境变量 / 工具参考。
--version, -v 输出版本后退出。

会话文件格式

会话文件格式

会话存储在 ~/.omp/agent/sessions/<cwd-dir>/<timestamp>_<id>.jsonl 下，按工作目录分组。一个文件对应一个会话；一行对应一条条目。条目绝不会原地重写——会话运行时可安全 tail -f，也可在回合中途安全复制。面向用户的恢复 / 分支 / 分享流程见 Sessions。

条目信封

每一行都是带有 type 判别器的 JSON 对象，含 8 字符 id、把它挂进树的 parentId，以及 timestamp。叶子不是一条条目——它是指向最新可达 id 的隐式指针。

字段 类型 说明
type string 判别器；见下方条目类型。
id string（8 hex） 随机 8 位十六进制，在文件内做冲突检查。
parentId string | null 父条目 id；首条消息为 null。
timestamp ISO 8601 UTC，秒级或更精细。

条目与会话 id

条目 id 是随机 8 字符十六进制字符串，在文件内做冲突检查。会话 id 是按时间排序的 UUID（v7），因此字典序即创建顺序，短前缀足以用于 --resume。分支与派生会保留条目 id；派生会把条目原样拷进新文件，给头部新的会话 id，并在 parentSession 记录来源。

会话头

每个文件的第一行是 session 头，携带 schema 版本、工作目录、可选标题，以及（派生时）parentSession 谱系标记。

字段 类型 说明
type "session" 头判别器。
version number Schema 版本；当前为 3。
id string 会话 id；与文件名一致。
cwd string 会话开始时的绝对工作目录。
title string? 选择器中显示的人类标签；由 /rename 设置。
parentSession string? 谱系标记：来源会话 id（派生）或会话文件路径（分支到新文件）。

消息条目

message 条目原样包装 agent 消息，含 role 与 content 数组。工具调用作为 toolCall 块挂在助手消息的 content 内；每条工具结果是独立的 message 条目，role: "toolResult"，像其他条目一样作为子节点挂进树。

内容块类型
块 角色 形状
text 任意 { type, text }
toolCall assistant { type, id, name, arguments } — id 是工具调用 id；arguments 是模型发出的 JSON。
toolResult 消息 独立条目 { role, toolCallId, toolName, content, isError } — toolCallId 匹配 toolCall.id；content 是内容数组（通常单个 text 块）。
thinking assistant { type, thinking } — 提供商支持时的扩展思考输出。

其他条目类型

类型 记录内容
model_change 活跃模型切换（/model 或角色轮换）。携带 model 与 role。
mode_change 计划模式开/关。
thinking_level_change 后续回合的扩展思考预算变更。
service_tier_change 提供商服务档（priority、batch）变更。
label 对另一条目的书签。携带 targetId 与 label；指向条目 id，压缩从不删除条目，因此标签会保留。
compaction 标记压缩替换了较旧回合的位置。携带 summary、firstKeptEntryId 与 tokensBefore。
branch_summary 被放弃分支的摘要，在 /tree 移走叶子时写入。
session_init 仅子代理会话；捕获系统提示、初始任务、工具列表及任何输出 schema，便于调试/回放。
custom / custom_message 扩展状态 — hooks、自定义工具或插件写入的不透明载荷。
ttsr_injection 记录已注入的 TTSR 规则名，使规则在每条分支上只触发一次。
mcp_tool_selection 内务 — 本会话暴露了哪些 MCP 工具。
