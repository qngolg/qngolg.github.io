Cursor 与 Claude Code 的上下文工程：为什么 Agent 不是「一股脑塞聊天记录」

Cursor 与 Claude Code 的上下文工程：为什么 Agent 不是「一股脑塞聊天记录」

做过 Agent 开发的人，多半都踩过同一个认知坑：

和大模型对话时，如果想让它「记得」历史上下文，只能把之前的聊天内容一股脑丢回去。

这句话在 API 协议层是对的——Transformer 对话接口本质无状态。但若据此认为 Cursor、Claude Code 也在每轮把完整 transcript 原样塞进 prompt，那就错了。

协议层仍是重放；产品层早已是上下文工程（Context Engineering）。
本文从无状态约束讲起，拆解 Cursor 与 Claude Code 的公开机制，并映射回 LangChain / LangGraph，方便自己做 Agent 时直接落地。

一、先分清两件事：无状态 API ≠ 全量聊天重放

1.1 模型侧确实没有「会话内存」

每次请求大致是：

所谓「记得上一句」，只是 harness（编排层）又把上一句——或其压缩版——放进了这次 prompt。模型服务端通常不会为你维护一份真正的跨请求工作记忆。

1.2 鸡肋的是策略，不是约束本身

层面 现状
模型 API 无状态，必须重放「工作记忆」
裸重放全部聊天原文 贵、慢、易脏上下文，确实很鸡肋
现代 Coding Agent 裁剪、外置、摘要、按需拉取、缓存前缀

一句话：必须有一份上下文进模型；但那份上下文不必等于「全部历史聊天原文」。

二、和 LangChain / LangGraph 对照：其实是同一条进化线

如果你用过 Memory、Checkpointer、Retriever，会发现 IDE Agent 并不是换了魔法，而是把同一套思路做成了默认生产流水线：

LangChain / LangGraph Cursor / Claude Code 中的对应
ConversationBufferMemory 短会话：最近若干轮原文
ConversationSummaryMemory 接近窗口上限时的 compaction / summarize
Token / message trim tool result 预算、microcompact、截断
Checkpointer + thread_id 会话持久化、可 resume
Retriever / RAG 代码索引、grep、语义搜索；历史当文件再搜
MessagesState + reducer 工具结果替换、摘要边界后丢弃旧消息
Subgraph / multi-agent Subagent、forked compaction agent

差别在于：Coding Agent 默认要对抗 工具结果爆炸 + 超长轨迹，所以策略更细、更「文件系统化」。

三、一次 Agent 请求里到底有什么？

以 Cursor 官方 context 环为例，窗口里大致是：

  1. System prompt：行为与格式约束
  2. Tools：工具定义（很吃 token）
  3. Rules / Skills 描述：静态前缀
  4. MCP 目录：可做成按需加载
  5. Subagent 说明
  6. Summarized conversation：旧轮次压缩结果
  7. Conversation：近期用户 / 助手 / 工具结果原文

再加上本轮动态拉进来的：打开文件片段、搜索命中、终端输出、@ 引用等。

聊天历史只是其中一块，而且常被压缩。 打开文件、规则、工具 schema、MCP，往往比「闲聊原文」更占窗口。

四、Cursor：从「塞满」到「按需发现」

Cursor 近年公开的关键转向叫 Dynamic Context Discovery（动态上下文发现）：少往窗口里静态塞东西，让 Agent 自己去捞相关上下文。

4.1 五条落地打法

  1. 长工具输出落盘
    Shell / MCP 大结果写成文件，上下文只留引用；需要时再 tail / read / grep。比直接截断更少丢信息，也更少被迫 summarize。

  2. 摘要后历史仍可搜
    Compaction 有损。Cursor 把 chat history 当文件；摘要丢了细节，Agent 还能回去搜补。

  3. Skills 渐进披露
    系统里常驻 name / description；正文与附属脚本按需再读——和 Agent Skills 的三级加载一致。

  4. MCP 工具按需发现
    不全量塞 schema。官方 A/B：在调用了 MCP 的 run 上，总 token 可减少约 **46.9%**（随安装的 MCP 数量波动大）。

  5. 终端会话当文件
    不必把整段终端输出 paste 进 prompt；Agent 可按需 grep 长日志。

抽象成一句话：状态外置到文件系统，上下文只持有指针 + 热数据。

4.2 窗口将满时：Summarize，而不是硬截断

接近 context 上限时，Cursor 会把较早对话压成摘要，给后续轮次腾地方；也可手动 /summarize。
社区反馈也提醒：压得过狠（例如压到极小摘要）可能出现「需求失忆、中途收工」——说明 压缩质量与保留策略 比「能不能压」更关键。

4.3 Composer：把摘要训进模型

通用模型靠「写几千字 summarization prompt」硬压；Composer 在训练里加入 self-summarization：

公开对比大致是：

  • 训练对齐后的摘要约 ~1k tokens（精心写的 prompt 基线常 >5k）
  • compaction 引入的错误约降 50%
  • 更能复用 KV cache

也就是说 Cursor 有两条线并行：

  • Harness 工程压缩（动态发现、落盘、摘要、历史可搜）
  • 专用模型学会怎么压（self-summarization 进 RL）

参考：Dynamic context discovery · Training Composer for longer horizons · Prompting agents

五、Claude Code：分层压缩，而不是一次 summarize

Claude Code（以及 Anthropic 对 context engineering 的公开描述）更强调：先便宜后贵。

5.1 各层在干什么

层级 作用 特点
Tool result budget 限制单次/累计工具输出进窗大小 最便宜的大头收益
Microcompact 清旧工具结果，保留最近热结果 常无需额外 LLM 调用
Session memory 持续维护结构化笔记 压缩时可复用，降低「再付一次摘要费」
Auto-compact 接近上限时结构化摘要 贵，但是主力恢复手段
Blocking / fallback 仍爆窗则拦住或删最旧 最后防线

例如在约 200k 窗口上，常见做法是在 ~167k 左右触发自动压缩——要给摘要输出和安全余量留空，而不是顶到 100% 再压。

5.2 好的摘要长什么样

生产级 compaction 通常不是「随便总结一下」，而是结构化保留：

  • 用户目标与原话要点（防需求漂移）
  • 关键技术决策
  • 改过的文件 / 路径
  • 错误与已尝试修复
  • 未完成待办与建议下一步

压完还会 rehydrate：重读最近文件、恢复 todo，再继续干——避免「摘要完大脑空了」。

5.3 Prompt Cache 与跨会话记忆

  • Fork + cache：摘要子代理尽量复用主会话前缀缓存，控制摘要成本。
  • 跨会话：CLAUDE.md、memory 文件等是持久指令面，不属于「聊天重放」，却同样塑造模型行为。

Anthropic 也在把 compaction、tool clearing 做成 API 能力（例如 cookbook 中的 context edits），方向很明确：上下文管理应成为基础设施。

七、为什么还要「重放」？成本与质量的三层视角

A. 语义层：必须有工作记忆

Agent 要连贯，就得知道：目标、决策、文件现状、未完成步骤。
无论原文还是摘要，总有一份要进 prompt。

B. 成本层：重放 ≠ 全价

Prompt Caching 让不变前缀（system、tools、rules）和稳定历史前缀大幅降价、降延迟。
你看到「又发了 100k tokens」，账单往往不是线性全价。

C. 质量层：塞太多会变笨

无关文件、过时 tool JSON、冲突指令，都会污染注意力。
现代 harness 的目标经常是 少而准，不是 多而全。

8.4 压缩时务必守住的不变量

  1. 用户原需求尽量 verbatim，防止需求漂移。
  2. 摘要是事务：成功才替换热历史；失败则回退。
  3. 压完要 rehydrate，不要只丢给模型一段摘要就指望它续上。
  4. 静态前缀稳定（tools / schema 顺序固定），方便 Prompt Cache。
  5. 触发阈值留 headroom，别等 100% 再压。

LangGraph 里的 RemoveMessage、自定义 reducer、checkpointer、store，足够实现上述大部分；Cursor / Claude Code 的优势在于 默认策略 + 与模型/训练对齐 + 为 coding 调过的阈值与格式。

九、常见误区

误区 更准确的说法
「上下文只能靠聊天记录」 聊天只是平面之一；代码、规则、文件、检索更重要
「窗口越大越好」 脏上下文会降智；有效信息密度更关键
「截断 = 压缩」 截断易丢关键信息；外置 + 可检索通常更优
「摘要一次就完事」 长任务会多次压缩；要防误差累积
「Prompt Cache 等于有状态」 Cache 降成本，不改变无状态语义

十、结论

回到开头那句「只能一股脑塞聊天记录」：

  • 若指模型 API 无状态：仍然成立，短期内也不会变成「服务端替你永久记住一切」。
  • 若指每轮必须塞全部历史原文：已经被淘汰，确实鸡肋。
  • 若指 Cursor / Claude Code 这类产品：核心竞争力已从「会不会调 LLM」，变成 上下文生命周期管理——什么进窗、什么外置、何时压、压什么、压完怎么恢复、静态前缀怎么缓存。

协议层：重放。产品层：外置状态 + 分层压缩 + 按需发现。

做过 LangChain / LangGraph 的人，其实已经站在同一条路上；差的往往不是新框架名词，而是有没有把这套管成默认、可观测、可恢复的流水线。
