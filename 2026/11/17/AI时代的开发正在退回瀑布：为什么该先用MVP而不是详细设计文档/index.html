AI 时代的开发正在退回瀑布：为什么该先用 MVP 而不是详细设计文档

标题不是夸张。过去一年我见到的「AI 开发流程」，绝大多数长这样：

这就是瀑布。只不过 1970 年代的瀑布靠人写文档，今天的瀑布靠模型写文档；以前的文档要花一周，现在的文档要花三十秒。

问题不在文档多，而在反馈晚。

一、先承认：AI 瀑布不是蠢，它有很强的诱因

把「为什么大家又回到瀑布」拆开，五个机制都在推着人往那边走。

机制 具体表现 真实性质
一次生成的心理 「上下文喂全它才能做对」 Agent 确实擅长一次吃完整上下文，人于是倾向于前置消灭不确定性
修改成本被感知放大 改 AI 写的代码要先读懂才能改 比自己写的代码贵，于是宁可前置设计换「一次做对」
文档成本塌陷 详细设计从人天变成分钟 成本趋零 → 供给爆炸 → 审查成为新瓶颈
工具在推 Kiro 的 requirements / design / tasks 三件套、GitHub Spec Kit 的 /specify → /plan → /tasks → /implement spec-driven 被做成了默认路径，不是可选项
demo 是完整的 演示要闭环，闭环要「做全」 展示需求压倒了验证需求

第一条和第三条是核心。

以前你写一份详细设计要三天，所以你会克制：只写关键决策，其余留白，边做边定。现在写一份详细设计要三十秒，克制消失了。设计文档从「压缩后的决策」膨胀成「模型对需求的全部想象」，然后人开始审它。

一个 2000 行的 spec 交给你，你会逐条看吗？现实是滑到底、看结构像样、批准。审批动作还在，审批功能已经失效。

二、伪瀑布：看起来严谨，实际是一堆未验证的猜测

传统瀑布虽然僵硬，但至少需求来自真实访谈、真实流程、真实数据。AI 时代的瀑布连这个都不成立。

维度 传统瀑布 AI 时代的瀑布
规格来源 用户访谈、现有流程、真实数据 模型根据一句话需求补齐
文档成本 高，所以克制 接近零，所以膨胀
审查方式 逐条对需求 读不下去，直接批准
错误的发现时机 集成测试 / 上线 同样晚，但错误更多
变更代价 文档链全废 文档链全废，且没人记得为什么这么写

模型在 spec 里补出来的东西是什么：字段名、状态机、边界条件、错误文案、「预留的扩展点」。这些不是需求，是模型的先验。

你批准它，等于把一堆猜测升格成合同；后面每一行代码都在这个猜测上叠加，而且因为有「设计文档」背书，猜错的地方反而没人质疑。

三个技术层面的放大效应：

  1. 长文档稀释注意力。 上下文里 80% 是设计文档、20% 是真实代码，Agent 越写越偏。这个机制在 Cursor 与 Claude Code 的上下文工程 里写过：塞进去的不等于用上的。
  2. 批次过大导致审查退化。 一次 20 个文件、3000 行 Diff，人审不动，只剩「测试绿了没」这一个信号。绿只证明代码和自己一致，不证明行为和需求一致。
  3. 错误被结构化了。 单个幻觉好发现；一整套自洽的、带章节编号的、有术语表的幻觉，看起来就是专业方案。

所以判断很直接：AI 没有让瀑布变好，它只是让瀑布变便宜了。而便宜的错误更危险，因为它会被大量生产。

三、敏捷在 AI 时代反而更划算

先算瀑布的心理账。人不是喜欢写文档，人是怕返工：

AI 把这张账改了，但只改了一半：

成本项 传统 AI 时代 变化
写第一版 人天 小时 大幅下降
改第二版 人天 小时（切片够小、上下文干净时） 大幅下降
验证需求对不对 要人等真实用户 还是要人等真实用户 一分没降
判断「做对了吗」 要人读代码 / 看结果 还是要人看结果 一分没降

结论就一句：实现变便宜了，但验证没变便宜。所以省下来的时间应该投到缩短反馈环，而不是投到提前写更多文档。

以前想省一次返工，你得花三天写设计文档，赌自己猜对了。现在花三小时上一个能点的 MVP，让人直接告诉你哪里不对——后者的信息量高一个数量级，而且不消耗你对需求的想象力。

四、怎么落地：六个动作

4.1 用垂直切片代替水平蓝图

瀑布的形状是水平的：先建所有表，再写所有 service，再写所有 controller。做完之前，什么都跑不起来。

敏捷的形状是垂直的：一条能点通的窄路径——一个页面 → 一个接口 → 一张表 → 一条真实数据。

第一刀要选最不确定的那条路径，不是最简单的那条。简单的那条切通了不提供任何信息；不确定的那条切不通，能提前三周告诉你这个方案不行。

4.2 规格写到「下一个可验证点」就停

超过一页，它就不再是规格，而是设计。设计应该写在代码里——代码是唯一不会过期的设计文档。

4.3 文档降级：ADR 替代设计书

该写 不该写
选了什么、为什么、什么条件下该推翻 每个类怎么组织、每个方法什么签名
不可逆的决策（见第六节） 未来可能用到但还没用到的扩展点
踩过的坑与结论 需求复述

详细设计一旦写出来就开始过期，而且没人读第二遍。可执行的契约——类型定义、schema、契约测试——比散文可靠得多，因为它们是会被编译和运行的。

4.4 把反馈环工程化

每轮结束必须满足三条，否则这一轮不算完成：

  1. 可运行：能启动、能点、能跑测试。
  2. 有门禁：typecheck / lint / 相关测试 / 一个 smoke 脚本。
  3. 可审：Diff 能在 15 分钟内读完。

第三点最容易被忽略。人审不动的时候，流程里所有的「评审」都会退化成点头。批次大小决定质量上限。

演示优于文档评审：让 Agent 把启动命令给你，自己点一遍。点不动的东西，写成多漂亮的文档都是不存在的。

4.5 计划性返工

第一版就是用来扔的。这句话得写进流程，不能只是心理建设：

  • 明确告诉 Agent：这一版只验证 X，其它一律可以丑、可以硬编码、可以只支持一个用例。
  • 预算按轮次分，比如 30 / 40 / 30，而不是一轮 100。
  • 第一版不抠命名、不抠抽象、不抠错误码文案——这些是可逆的，留到方向确定之后。

怕返工的人写瀑布；把返工预算显式排进计划的人才能敏捷。

4.6 每轮重置上下文

新 loop 从干净的上下文开始：喂当前代码 + 本轮目标，不喂全部聊天历史。

上一轮留下的约束还有效的，压缩成五行写进本轮提示；已经失效的文档直接删掉，不要留在仓库里当噪音。留着一份过期设计文档，比没有设计文档更糟——下一轮 Agent 会认真执行它。

五、两种模式对照

维度 AI 瀑布 AI 敏捷
起点 一句话需求 → 完整设计文档 一句话需求 → 最不确定的那条路径
第一个交付物 设计评审通过 能点的东西
规格粒度 全量、预测性 增量、可验证
批次 一次全量实现 垂直切片，小 PR
验证方式 文档评审 + 最后集成 每轮可跑 + 人点一下
需求变化 文档链全废 下一切片换方向
主要风险 错误的规格被高效执行 局部返工
人的时间花在 审文档、点头 定验收、看演示、砍范围

最后一行是全部差别的浓缩：AI 瀑布把人的时间花在审文档上，AI 敏捷把人的时间花在看结果上。

而人的时间是这套流程里唯一没被 AI 降价的资源。

六、什么时候必须写详细设计

说清楚边界，不然这篇就成了反对设计的口号。

区分标准只有一条：不可逆还是可逆。

必须详细设计（不可逆） 可以边做边定（可逆）
数据模型与迁移（改一次要停机 / 回填） 内部函数与模块边界
对外 API 契约（有第三方消费者） UI 布局与交互细节
权限与安全边界 日志、指标、文案
钱、账、审计 配置结构
跨团队 / 跨仓库契约 缓存策略（能回滚）
合规要求 内部工具与脚本

一句话：为不可逆的部分写文档，为可逆的部分写代码。

大多数功能里，不可逆的部分只占 10%——一张表的结构、一个对外接口的形状。为这 10% 认真写，剩下 90% 让代码自己说话。把 100% 都写成文档，等于把 90% 的可逆空间提前锁死成猜测。

七、和 TDD 那篇矛盾吗

不矛盾，但要分清楚两件事。

AI 时代的 TDD 里说「先写失败测试，再让 Agent 实现」。这篇说「别先写详细设计」。区别在可执行性：

失败测试 详细设计文档
性质 行为契约，可执行 对实现的预测，不可执行
写错的后果 直接红灯，当场发现 被后续所有代码继承
需求变了 删用例、改断言，代价明确 文档链作废，且没人知道该改哪段
谁在验证 测试运行器 人的耐心

详细设计预测怎么做，失败测试定义做对了是什么样。前者制造瀑布，后者恰恰是敏捷需要的东西——它是每个切片最小的验收锚点。

所以正确的组合是：一页纸规格 + 一个能点的切片 + 几条验收测试。 不需要设计书。

把上面所有东西压成一段，直接对 Cursor / Claude Code / omp 说：

三个细节值得单独拎出来：

  • 「可以硬编码、可以丑」 要明确写。不写，模型会自带工程洁癖，把原型当产品做，第一轮就给你整套抽象。
  • 「列出假设」 是替代设计评审的关键动作。设计文档的隐藏价值是暴露假设，这件事一行清单就能做到，不需要 2000 行。
  • 「Stop」 是边界，不是客气。不写 Stop，Agent 会把 Red 和 Green 一口气吞掉，你连插话的机会都没有。

节奏建议：一天 2–3 轮，每轮 30–90 分钟。超过 90 分钟还没有东西能跑，就是切片切大了——回去切小，而不是补文档。

九、小结

四句话：

  1. AI 让写文档变便宜，不等于让文档变正确。
  2. 瀑布的根因不是爱写文档，是怕返工；AI 把返工变便宜了——前提是切片够小、上下文干净。
  3. 先上一个能点的 MVP，用真实反馈替换模型猜测。
  4. 只为不可逆的东西写详细设计。

你不是在给 AI 写需求说明书。你是在用它把「下一个能验证的东西」更快做出来。

顺序反过来，工具再强也只是把错误执行得更快。
