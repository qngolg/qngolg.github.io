DeepSeek Harness 详解：一切皆插件的 Agent 架构与插件开发实战

发表于2026-08-21|更新于2026-08-21|AI
|浏览量:

DeepSeek Harness 详解：一切皆插件的 Agent 架构与插件开发实战

配套阅读：从零写一个 Pi Extension（另一套 Agent 扩展体系的对照）· 官方 README · 架构文档（中文） · Cordis 入门

目标：讲清楚 dsh 为什么把”模型之外的一切”都做成插件、插件有哪几种典型模式、怎么写一个自己的插件，以及从本地开发到打包安装的完整应用流程。

一、背景：什么是 DeepSeek Harness

2026 年 8 月，DeepSeek AI 开源了 DeepSeek Harness（简称 dsh）——一个基于 Cordis 插件框架的 agent harness，采用 「一切皆插件」 架构，MIT 协议。它遵循的编程范式有配套论文：A Programming Paradigm for Spatiotemporal Composability。

先厘清定位：Harness 不是模型。Model + Harness = Agent——模型负责推理，harness 负责模型之外的一切：工具、文件系统、沙箱、权限、会话、UI，甚至 agent loop 本身。

dsh 的特殊之处在于：模型的适配器、工具注册表、会话日志、agent loop 全部都是插件，因此每一部分都可以从配置上替换，而不需要 fork 源码。它当前处于 开发者预览（Developer Preview） 阶段，迭代很快，官方明确提示”未来将出现破坏兼容性的变更”。

下面从架构设计模式讲起。

二、架构设计模式

2.1 微内核：没有特权内核

dsh 是典型的微内核 + 插件架构：

  • 内核只提供 Cordis 插件框架本身（上下文、事件、副作用管理）；
  • 产品的每一部分（模型适配器、工具、会话、UI……）都是挂载在框架上的插件；
  • 不存在需要打补丁的特权内核。扩展 dsh 的方式就是把插件挂载到其他插件旁边；
  • 所有注册都是可逆副作用——插件卸载时，它注册的工具、监听器、服务自动撤销。

向 Cordis 树贡献内容的核心包：

包 职责 ctx 键
core/session 仅追加的 SessionEvent 日志和内存存储 ctx.sessions
core/system-prompt 提示词片段与工具 schema 的组装 ctx.systemPrompt
core/tools 作用域化的工具注册表和带把关的执行流水线 ctx.tools
core/agent Agent 接口、活跃 agent 注册表和 agent/* 事件 ctx.agents
core/agent-loop 实现 Agent 接口的默认驱动器 ctx.agentLoop
core/scope 按 agent 划分作用域的注册原语 库，无 ctx 键
llm/llm 消息与流式词汇表，以及适配器 seam ctx.llm

agent-loop 本身也是可替换的：它是”实现 Agent 接口的默认驱动器”。想改变 agent 的思考循环，不是改内核，而是换一个 loop 插件。

2.2 Cordis 的五个核心思想

Cordis 是 dsh 底层的插件框架（vendored），写插件前必须理解这五件事：

  1. 插件是实现了 Service 的对象：可以是一个带可选 inject 和 apply(ctx) 的函数，也可以是一个 Service 子类。
  2. 上下文是服务的仓库：服务在 ctx 上占有稳定的键（ctx.tools、ctx.llm、ctx.sessions），其他插件按键查找服务，而不是 import 具体实现——这就是”面向接口”的解耦。
  3. 用 inject 声明依赖：声明了所需服务的插件会等到这些服务就绪后才执行 apply，加载顺序由依赖关系表达，而非手动排启动顺序。
  4. 类型化事件通信：服务通过 TypeScript declaration merging 声明事件名，再以 emit / waterfall / parallel / serial 四种方式派发。
  5. 注册是可逆的副作用：提示词片段、工具 schema、适配器、提供方、监听器都通过 ctx.effect() / ctx.on() 安装，重载与卸载时按序撤销。

2.3 事件：扩展点与四种分派模式

事件就是扩展点。 每种事件的分派模式是公开契约的一部分：

模式 是否 await 派发顺序 有返回值
emit 否 按注册顺序观察 无
waterfall 否 按注册顺序观察 有
parallel 是 所有监听器并行观察 无
serial 是 按注册顺序观察 有

waterfall 是”环绕中间件”：监听器收到 (...args, next)，调用 next() 把（可能被包装的）结果委托给下一个服务；不调用 next() 直接返回即短路。策略类监听器”拥有决策”时直接短路，只做注解或观察的监听器必须委托。

dsh 的事件分三个域，选对事件域是大多数改动的第一个决定：

  • 会话事件：追加到日志并通过 session/event 广播的持久事实（turn/*、step/*、user/message、assistant/*、tool/*）。需要在重新加载后仍然存在的事实用它。
  • Agent 事件（agent/*）：携带活跃 Agent 的实时事件（inbox、步骤、状态、请求、验证、续跑）。要观察或拦截进行中的工作用它。
  • 能力事件：无导入循环地为某个 seam（fs/*、tools/*、telemetry/*）附加策略和适配器。

2.4 轮次流程：事件怎么驱动 Agent 干活

一个步骤是一次模型请求加上它调用的工具；一个轮次包含零个或多个步骤，在领到首条输入时打开，在不再欠任何工作时关闭。驱动器（agent-loop）就是这张图的实现：

要点：

  • agent/pre-step 决定模型看到什么：监听器可改写已领取的消息，也可直接拒绝；首次领取被拒绝或改写为空时，仍会关闭一个不含步骤的持久轮次。
  • agent/pre-step、agent/request、llm/stream、三个 tools/* 事件是 waterfall，监听器必须 next() 才能委托下去；agent/turn-stopping 是 serial 事件。
  • 会话日志是模型所见上下文的来源。deriveMessages() 从日志投影出模型历史，原始 assistant/chunk 事件保证回放与 UI 保真；fork、恢复、transcript、遥测、持久化全部派生自该事件流。
  • 运行时不变量：**”模型可见即已记录”**——抵达模型请求的一切都必须能从日志重建。因此新增一项模型可见输入 = 新增一个会话事件。

2.5 Profile 与组合包：分层叠加的配置树

运行中的 dsh 是一棵插件树，由启动时按序叠加的各层组合而成：

  • 组合包（bundle）是 Cordis 配置项及其挂载代码的分发格式（npm 包 + 一份 patch 文件），回答”这个包贡献什么”。
  • Profile 是存放在 Harness home（$DSH_HOME/profiles/<name>）中的具名组装，回答”这套配置由哪些组合包按什么顺序组成”。web 和 headless 作为模板随发行版交付：dsh-base 是每套 profile 的第一层（模型适配器、工具、持久化、沙箱与审批、设置、凭据、遥测），dsh-web-app 增加浏览器应用，dsh-headless 增加一次性运行器且不带服务器。

生效配置在空根之上按顺序逐层组合：

  1. profile 的 dsh.profile.bundles 所列组合包 patch，按列表顺序；
  2. profile 自己的 cordis.patch.yml；
  3. home 级 $DSH_HOME/cordis.patch.yml（机器本地偏好）；
  4. 每个 --patch <path> overlay，按 argv 顺序。

patch 按 id 定位条目并替换整条 config（不是深合并），后应用的层按行胜出。查看机器实际启动的配置树：

打印出的任何条目，都可以由你自己的 patch 替换。

2.6 能力 Seam：替换一个提供方，改变整个产品

Seam 是一项可替换能力，包含三种角色：

  • Service Definition：声明接口；
  • Service Provider：实现它；
  • Consumer：使用它（通常是面向模型的工具）。

一个包可合并承担多个角色，但单一角色本身不是 seam——添加一项能力意味着把三者一并设计。这就是”替换一个提供方就能改变整个产品”的原因：

  • 文件系统与进程提供方共享同一个执行世界，把 fs 提供方指向远程沙箱，Bash、PTY、LSP 一并搬了过去，无需提供方专用 fork；
  • subagent 提供方在同一接口之后千差万别：新建一个子 agent、把一个轮次委派给另一个产品（dsh-subagent-spawn-in-process / -fork / -acp / -codex / -claude-code）。

新行为应该归属到哪个扩展点，官方有一张明确的映射表（节选）：

目标 机制
添加模型提供方 在 ctx.llm 上注册其适配器
添加面向模型的能力 在 ctx.tools 上注册；schema 自动加入提示词组装
添加 shell 执行 注册 ctx.shell 后端
添加用户命令 在 ctx.commands 上注册；无需模型轮次即可分派
拦截请求、工具或轮次 使用相应 agent/* 或 tools/* 事件
添加模型可见上下文 调用 agent.inject()，落到下一次获准的请求
添加持久会话状态 扩展 SessionEventMap，从日志渲染与回放
添加 UI 或编辑器集成 驱动 ctx.agents 并从 session/event 渲染

3.2 工具插件：给模型加能力

工具注册在 ctx.tools 上，defineTool 是首方工具的强类型助手（MCP 来源的原始 JSON-Schema 工具也直接被 register 接受）。注册即副作用：卸载插件即注销工具，schema 自动流入提示词组装。

execute 契约的几条硬规则：

  • 参数替你校验：defineTool 在 execute 前用统一 schema 校验模型生成的参数（类型、必填、字面量约束、互斥联合、嵌套值），args 与推断类型一致；
  • 执行身份受保护：参数被物化为无损 JSON 并冻结，exec.token、callId、signal 在派发期间不可变；
  • 只返回一个规范值：output.schema 声明返回结构，execute 只返回推断值，注册表快照、校验、冻结后交给 output.render 转成模型可见内容；
  • **抛错或返回非法值 = isError**；
  • **尊重 exec.signal**：触发时取消进行中的工作；
  • **长任务走 ctx.jobs.start({ kind, label, owner: exec.agent, run })**，返回 { kind: 'background', jobId } 这样的规范句柄，配合 run_in_background 开关。

3.3 Hook 插件：在流水线上插一道闸（权限门）

工具流水线上有多个可拦截点，权限、沙箱、plan-mode 都是”在 tools/pre-execute 返回一个类型化决策”：

拦截点的选型规则：

  • tools/pre-execute：可重排的策略层（allow/deny/ask）；
  • ctx.tools.guard()：最终单调拒绝，后续监听器无法撤销；
  • tools/execute：包住实际派发生命周期（超时、重试、指标；只有 exec.signal 可替换）；
  • tools/post-execute：替换展示内容或返回值、拦结果、附加模型可见上下文；
  • tools/result：只读地观察不可变的最终规范化结果。

3.4 UI 插件：从事件流渲染，用 API 驱动

UI 是会话事件流的消费者：从 session/event 渲染（assistant 增量、轮次/步骤边界、工具活动），用 agent.followup() / agent.steer() 把输入喂回去：

要给内置 Web Client 的聊天界面加业务行，则注册 ConversationNodeDefinition + keyed Chat renderer（参考 Conversation Node 指南）。

3.5 协议驱动：把外部协议接到 ctx.agents

协议驱动把线上的对端适配到 ctx.agents——stdio 驱动持有 stdout，通过工厂创建/恢复 agent，把协议请求映射到 followup() / cancel()，用 AgentHandle.dispose() 拆卸（到达 quiescence）。官方参考实现是 @deepseek-ai/dsh-acp：通过 Agent Client Protocol JSON-RPC stdio 暴露全新文本会话，发出已提交的 assistant 文本，并为它拥有的 agent 注册一次性机器权限应答器。

3.6 特性 → 机制映射：每个产品功能都落在扩展点上

官方用一张表证明”微内核”这个主张——没有任何一行改动循环本身（节选）：

产品特性 插件机制
Hook 系统（用户 + 项目级） agent/session-start、agent/pre-step、agent/request、tools/pre-execute、tools/post-execute、agent/turn-stopping 的监听器
MCP 每个 server 一个插件：发现工具 → ctx.tools.register()
Skills section + 工具注册；调用时 inject() 技能内容
内存 / Memory section provider + 工具
定时任务（cron） 插件注册模型可调度的工具；定时器触发 → 空闲时 followup() / 忙碌时 inject()
Context 压缩 ctx.compaction seam + dsh-compaction-basic
子 agent 委派 ctx.subagents 提供方注册表 + dsh-tool-subagent
插件热重载 每次注册都是 ctx.effect，vendored HMR 直接可用

五、应用流程

5.1 启动与日常使用

  • Web UI：npx @deepseek-ai/dsh web 或 pnpm dsh web，默认 http://127.0.0.1:3080，本机启动自动开浏览器；SSH 启动只打印宿主 URL；--no-open 只跑服务器。
  • Headless：dsh --profile headless 提供一次性运行器，不带服务器。
  • 模型提供方在 Web UI 的 providers 页面配置。

5.2 层顺序与覆盖规则（决定”谁的配置生效”）

生效配置按序叠加：bundle 列表 → profile 的 cordis.patch.yml → home 级 cordis.patch.yml → 每个 --patch overlay。注意：

  • patch 按 id 覆盖前层整行 config，必须重述该行需要的每一个键，不是只写改动的键；
  • 你的 bundle 可以被用户在 profile 的 patch 中覆盖，因此给出用户大概率会保留的默认值，把其他交给 schema；
  • 内置组合包名始终从 dsh 安装目录解析，你的 bundle 可以放心依赖 @deepseek-ai/dsh-base。

5.3 从 GitHub 直接安装（及风险）

git 安装拉取的是源码不是构建产物，所以：

  • 作者：提供 prepare 脚本（pnpm 在 git 安装后运行它）从源码构建发布入口，且必须自包含（不能假设 monorepo checkout 等开发环境上下文）；

  • 用户：为构建授权。pnpm ≥10 默认拒绝运行 git 依赖的 prepare 脚本，首次 add 会失败；把 pnpm 打印的包键写进该 profile 的 pnpm-workspace.yaml：

    请如实看待这项授权：它允许该包代码在安装时于你的机器上执行，且不在 agent 沙箱内。只对源码可信的包授权，并锁定 commit（github:you/hello-plugin#<sha>），防止后续推送悄悄改变实际运行的内容。

不想让用户做授权，就分发构建产物：

  • 发布 npm：pnpm publish 时构建好 lib/，dsh plugin add your-package 装的就是预构建代码；
  • 交付 tarball：pnpm pack 打包，用户 dsh plugin add ./hello-plugin-0.1.0.tgz。

5.4 插件生态与发现

  • 官方欢迎通过 GitHub Discussions 反馈；
  • 为插件仓库添加 dsh-plugin topic 便于被发现；
  • 参考实现的活例子：packages/shell/tool-bash（生产级工具三件套）、packages/acp/acp（协议驱动）、turtle-ui（git 安装 + prepare 构建的可用范例）。

六、总结

  • 架构上，dsh 用 Cordis 微内核把”模型之外的一切”做成插件：核心包只贡献服务（ctx.tools/ctx.llm/ctx.sessions…），agent loop 本身可替换，注册即副作用、卸载即撤销，事件是唯一的扩展点。
  • 模式上，工具、Hook 权限门、UI、协议驱动、服务提供方五类插件各有固定落点：能力加在 ctx.tools，策略挂在 tools/* 事件，UI 消费 session/event，外部协议接 ctx.agents。
  • 开发上，一个函数 + apply(ctx) 就是插件，defineTool 加 schema 就有工具，effect 保证可逆，配置走 Schemastery schema 校验。
  • 应用上，组合包（bundle）是分发单元，profile 是有序组装，dsh plugin add 即装即用，四层 patch 决定了谁覆盖谁。

横向对比其他 Coding Agent：Claude Code / Codex 把扩展做成”钩子 + 外部协议”的封闭面，dsh 则把整个产品做成了开放面——产品差异面就是插件面。如果你是”想深度定制 agent 行为”的团队，dsh 是目前少见的、每一层都能从配置替换的选择。

最后提醒一句：它仍处于 Developer Preview，官方明确会有破坏性变更；用插件（而不是 fork）去跟随迭代，正是这套架构给的生存策略。
